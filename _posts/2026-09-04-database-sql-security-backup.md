모두의연구소 "바이브 코딩으로 웹 만들기" 과정 5강 **"데이터베이스 — 고객의 데이터는 어떻게 관리될까"** 를 정리합니다.

지난 시간에 배운 백엔드가 **눈에 안 보이는 주방**이었다면, 오늘은 **재료를 두는 창고** 이야기였습니다. 주방이 주문을 처리하는 건 알았는데, 한 가지가 빠져 있었거든요 — 만든 데이터를 어디에 둘까?

지금까지 제가 다룬 데이터는 전부 **컴퓨터의 잠깐 기억(메모리)** 에만 있었습니다. 그래서 새로고침하면 사라졌죠. 서비스가 되려면 데이터가 남아야 하고, 그 영구 창고가 데이터베이스입니다. 오늘 배운 한 문장은 이겁니다.

> **데이터베이스는 서비스의 '기억'이다.** 넣고 꺼내는 코드(SQL)는 AI가 쓰지만, 무엇을 어떤 모양으로 저장할지 · 어떤 DB를 고를지 · 어떻게 안전하게 지킬지는 내가 정한다.

## 1. 데이터베이스는 '쌓아 두는 곳'이 아니다

두 가지 그림이면 충분했습니다.

**도서관** — 책이 수만 권 있어도 원하는 책을 금방 찾습니다. DB가 도서관, 데이터가 책, 관리 소프트웨어가 사서입니다.
**마법 장난감 상자** — 장난감을 마구 넣어도 "파란색 자동차만 다 꺼내 줘" 하면 그것만 정리해서 꺼내 줍니다.

핵심은 DB가 그냥 쌓아 두는 곳이 아니라 **원하는 것만 빠르게 찾아 주는 곳**이라는 겁니다.

### 그럼 엑셀이랑 뭐가 다른가

작을 때는 엑셀로도 됩니다. 다른 건 세 가지입니다.

1. **규칙(스키마)이 있다** — "이 표에는 이름·가격·분류가 들어간다"처럼 모양을 정해 두고 **강제**합니다. 그래서 뒤죽박죽이 안 됩니다.
2. **수만 건에서도 순식간에 찾는다** — 엑셀은 커지면 느려지고 멈추지만, DB는 그러라고 만들어진 물건입니다.
3. **여러 사람이 동시에 안전하게 쓸 수 있다** — 서비스에는 필수죠.

### 잠깐, 얼마나 커질 수 있나

규모 감각을 주려고 나온 사례가 인상적이었습니다. 미국 의회도서관은 **1억 7,800만 점 이상**을 소장하고 디지털 보존만 페타바이트 단위입니다. CERN의 LHC는 **초당 약 10억 번**의 입자 충돌로 이론상 초당 1페타바이트가 쏟아지는데, '트리거'가 의미 있는 **1%도 안 되는 양**만 골라 저장합니다. 그렇게 걸러도 2023년에 1엑사바이트를 넘었고요.

여기서 배운 게 있습니다 — **큰 데이터에서는 무엇을 저장할지 고르는 일이 저장장치 크기만큼 중요하다.**

## 2. 왜 종류가 이렇게 많을까 — 60년의 역사

"DB도 종류가 왜 이렇게 많아?"는 프레임워크 때와 똑같은 질문이었습니다. 답도 같았습니다 — **매 시대 병목이 달랐고, 그때마다 새 도구가 나왔을 뿐**입니다.

| 시기 | 무슨 일이 |
|---|---|
| 1960년대 | 그냥 파일에 적어 둠 → 양이 늘자 찾기가 지옥 |
| **1970년** | 에드거 코드, "표로 나누고 관계로 잇자" 논문 |
| 1974년 | 질의 언어 SEQUEL 등장 (뒤에 SQL로 개명) |
| 1979년 | 첫 상용 관계형 DB (Oracle) |
| 2000년대 | 데이터 폭증 → NoSQL 등장 |
| 오늘날 | 클라우드 DB — 비전공자도 무료로 진짜 DB를 씀 |

### 뒷이야기 넷이 재미있었습니다

**① IBM은 자기 논문을 망설였다**
1970년 당시 데이터는 나뭇가지처럼 얽힌 구조라, 뭘 꺼내려면 가지를 타고 들어가는 전용 프로그램을 매번 짜야 했습니다. 코드는 "그냥 표로 두고 관계로 이으면 안 되나?"라는 논문을 냈죠. 그런데 정작 **IBM이 미지근했습니다.** 이미 IMS라는 제품이 잘 팔리고 있어서, 새 아이디어가 효자 상품을 갉아먹을까 봐요.

**② 'SQL'은 원래 '시퀄'이었다**
처음 이름은 **SEQUEL**(Structured English Query Language) — 영어 문장처럼 읽히게 만들자는 뜻이었습니다. 그런데 이게 영국 항공기 회사 **상표**로 이미 등록돼 있었어요. 변호사 편지를 받고 모음을 빼서 **SQL**이 됐습니다. 사람마다 "에스큐엘"이라 하기도 "시퀄"이라 하기도 하는 이유가 여기 있습니다. 둘 다 맞습니다.

**③ IBM보다 빨랐던 신생 회사**
코드의 논문을 읽고 "이거 돈이 되겠다"고 확신한 사람이 **래리 엘리슨**입니다. 1977년 창업해 1979년 첫 상용 관계형 DB를 내놨는데, 아이디어를 만든 IBM(1981년)보다 **2년 앞섰습니다.** 첫 제품 버전을 '1'이 아니라 '2'로 붙인 것도 재미있습니다 — 갓 나온 소프트웨어를 아무도 안 믿을까 봐, "이미 한 번 개선했다"는 인상을 주려고요.

**④ NoSQL의 진짜 뜻은 'Not Only SQL'**
2009년 개발자 모임에서 검색하기 좋은 이름을 찾다 붙은 게 'NoSQL'인데, 이게 "SQL 쓰지 말자"로 오해를 샀습니다. 그래서 나중에 **"Not Only SQL"** 로 다시 해석됐죠. 실제로 NoSQL은 관계형을 대체한 게 아니라 **용도별 선택지**입니다.

### 성격만 알면 됩니다

| | SQL | NoSQL |
|---|---|---|
| 생김새 | 엑셀 같은 표 | 유연한 문서·덩어리 |
| 규칙 | 엄격 | 느슨하거나 없음 |
| 강한 곳 | 관계가 분명한 데이터, **정확성**(돈·주문) | 대규모·빠르게 변하는 데이터 |
| 대신 포기 | 유연함 | 표끼리 잇기, 엄격한 거래 일부 |

넷플릭스·우버도 둘 다 씁니다. 다만 **처음 만드는 서비스라면 SQL이 무난한 기본값**입니다.

## 3. SQL은 거의 영어입니다

가장 마음이 놓였던 대목입니다. 강의가 계속 강조한 건 **"외우지 마라, 알아보기만 해라"** 였습니다.

```sql
SELECT 이름, 가격 FROM 상품 WHERE 분류 = '케이크';
```

풀어 읽으면 이렇습니다 — **"상품 표에서(FROM) 분류가 케이크인 것들의(WHERE) 이름과 가격을 줘(SELECT)."** 정말 영어 문장 순서 그대로입니다.

넣고·고치고·지우는 것도 단어만 바뀝니다.

- `SELECT` — 꺼내 보기
- `INSERT` — 새로 넣기
- `UPDATE` — 고치기
- `DELETE` — 지우기

이 넷을 묶어 **CRUD**라고 부릅니다. 대부분의 서비스는 결국 **이 네 동작의 반복**입니다.

## 4. 데이터의 모양 — 표, 행, 열, 그리고 키

관계형 데이터베이스는 결국 **표**입니다. 엑셀을 떠올리면 됩니다.

- **표** = 한 종류 (상품 표)
- **행(row)** = 한 건 (딸기 케이크 하나)
- **열(column)** = 항목 (이름, 가격, 분류)

그리고 표끼리 **관계**로 잇습니다. 주문 표는 "어떤 상품을 샀는지"를 상품 정보 통째로가 아니라 **고유 번호(ID)로 가리킵니다.** 이 "표로 나누고 관계로 잇기"가 **관계형(relational)** 이라는 이름의 뜻이었습니다.

### 왜 나누나 — 쇼핑몰 예시

한 덩어리로 뭉치면 이렇게 됩니다.

> "홍길동이 3월 2일에 초코케이크 2개를 12,000원에 샀고, 홍길동의 주소는 …"

주문이 100건이면 **홍길동 주소가 100번 적힙니다.** 그래서 성격이 다른 것끼리 표를 나눕니다.

| 표 | 담는 것 | 예시 한 줄 |
|---|---|---|
| 회원 | 사람 정보 | 1번 · 홍길동 · 서울… |
| 상품 | 파는 것 | 7번 · 초코케이크 · 12,000원 |
| 주문 | 언제 누가 무엇을 | 55번 · **1번 회원** · **7번 상품** · 2개 · 3/2 |

핵심은 주문 표가 이름·주소를 다시 적지 않고 **"1번 회원"이라고만 가리키는 것**입니다. 주소가 바뀌면 회원 표 한 곳만 고치면 끝이죠. 표를 잇는 이 번호를 **키(key)** 라고 부릅니다.

## 5. 표는 어떻게 이어지나 — 1:N과 N:M

관계는 대부분 두 가지 모양이었습니다.

**① 일대다 (1:N) — 한쪽만 여러 개**
회원 1명은 주문을 여러 건 남기지만, 주문 1건은 한 회원의 것입니다. 이럴 땐 주문 표에 **"누구의 주문인지" 칸 하나**만 넣으면 끝입니다. 블로그의 '글 1개 ↔ 댓글 여러 개', 유튜브의 '채널 1개 ↔ 영상 여러 개'가 모두 같은 모양입니다.

**② 다대다 (N:M) — 양쪽 다 여러 개**
학생 1명은 여러 수업을 듣고, 수업 1개도 여러 학생이 듣습니다. 이건 양쪽 어디에도 상대를 다 적을 수 없습니다(한 칸에 여러 개를 욱여넣으면 검색이 깨집니다). 그래서 **연결 표**(수강신청 표)를 하나 새로 만들어 학생 번호와 수업 번호를 짝지어 한 줄씩 적습니다. 그러면 N:M이 **'연결 표를 사이에 둔 두 개의 1:N'** 으로 깔끔하게 풀립니다.

판단 감각은 하나면 됩니다.

> **"A 하나가 B 여럿을, 동시에 B 하나도 A 여럿을 갖나?"**
> 그렇다면 N:M이라 중간 표가 필요하고, 한쪽만 여러 개면 1:N입니다.

## 6. DB는 왜 빠를까 — 책 뒤 '찾아보기'

수만 권 중에서 원하는 책을 도서관이 금방 찾는 비결, DB도 같은 트릭을 씁니다. **색인(index)** 입니다.

두꺼운 전공책 맨 뒤에 "삼투압 → 245쪽" 같은 찾아보기가 있죠. 그 덕에 처음부터 한 장씩 넘기지 않고 바로 갑니다. DB의 색인이 정확히 이겁니다. 자주 찾는 항목(이메일·상품명)에 색인을 만들어 두면 수백만 건에서도 순식간에 찾고, **없으면 처음부터 전부 뒤집니다.**

### 다만 공짜가 아닙니다

넣고 고칠 때마다 색인도 갱신해야 하고 공간도 듭니다. 그래서 배운 결론이 인상적이었습니다.

> **빠른 DB는 색인이 많은 DB가 아니라, 실제 질문에 맞는 최소한의 색인을 가진 DB다.**

비전공자를 위한 실전 요령도 좋았습니다. AI에게 그냥 "색인 넣어줘"라고 하지 말고, 먼저 **"사용자는 자기 주문만 최근순 20개 본다"** 처럼 **실제 화면의 질문**을 문장으로 주라는 겁니다. 그래야 맞는 색인을 제안합니다.

## 7. 반쪽만 되면 안 된다 — 트랜잭션과 ACID

은행에서 A가 B에게 만 원을 보냅니다. 컴퓨터가 할 일은 둘이죠 — ① A에서 만 원 빼기 ② B에 만 원 넣기. 그런데 ①을 하고 ② 직전에 정전이 나면? **A 돈은 사라졌는데 B는 못 받았습니다.**

그래서 DB는 여러 동작을 **하나의 묶음(트랜잭션)** 으로 처리합니다. 원칙은 딱 하나입니다.

> **"전부 되거나, 전부 안 되거나."**

이 성질을 포함한 네 가지 약속을 묶어 **ACID**라고 부릅니다.

| | 뜻 |
|---|---|
| **A** 원자성 | 반쪽 실행은 없다 |
| **C** 일관성 | 규칙에 어긋난 상태로는 안 끝난다 |
| **I** 고립성 | 동시에 여러 명이 만져도 안 꼬인다 |
| **D** 지속성 | 됐다고 하면 정전이 나도 남는다 |

친구 둘이 마지막 티켓 한 장을 거의 동시에 눌러도 둘 다에게 팔리지 않는 게 이 장치 덕분입니다. 외울 건 없고 **"돈·주문·예약처럼 틀리면 큰일인 데이터는 SQL DB가 안전하다"** 는 감만 있으면 된다고 했습니다.

⚠️ 그리고 못을 박습니다 — **ACID는 백업이 아닙니다.** 실수로 지운 걸 되돌려 주지는 않습니다.

## 8. 같은 걸 두 번 적지 않기 — 정규화

단골 손님의 주소가 바뀌었는데, 그 손님의 주문 100건에 주소를 매번 적어 뒀다면? **100군데를 다 고쳐야 하고, 하나라도 놓치면 데이터가 서로 안 맞습니다.**

그래서 관계형 DB는 "같은 정보는 한 곳에만 적고, 나머지는 그걸 가리키게" 합니다. 이 정리정돈이 **정규화(normalization)** 입니다.

설계를 직접 할 필요는 없다고 합니다. 제가 할 일은 이 의심 하나입니다.

> **"이 정보, 여기저기 똑같이 적히고 있진 않나?"**

그리고 서비스가 자라면 표 구조 자체를 바꿔야 할 때가 옵니다. 데이터가 이미 든 DB의 구조를 안전하게 바꾸는 작업이 **마이그레이션(migration)** 이고, "DB 구조 변경을 Git처럼 이력으로 관리하는 것"이라 생각하면 된다고 했습니다.

딱 하나만 기억하라고 했습니다 — **칸을 삭제하는 변경은 그 안의 데이터가 영구히 사라질 수 있습니다. 구조를 바꾸기 전엔 반드시 백업.**

## 9. 사용자가 생기면 — 회원가입, 로그인, 세션

로그인은 화면 기능 같지만 뿌리는 **데이터**였습니다. 회원 표 하나가 필요하고, 회원가입은 행 하나 넣기(Create), 로그인은 그 이메일로 행을 찾아(Read) 비밀번호를 대조하는 것 — 결국 **CRUD의 조합**입니다.

꼭 지킬 세 가지를 배웠습니다.

1. **비밀번호는 절대 원문으로 저장하지 않는다** — 해시(솔트 + bcrypt)를 저장합니다. 칸 이름을 `password`가 아니라 `password_hash`로 두면 "원문 금지"를 스스로 상기하기 좋다는 팁이 좋았습니다.
2. **이메일은 유일(unique) 제약을** — 없으면 중복 계정과 로그인 혼란이 생깁니다.
3. **필요한 것만 모은다.**

### 로그인이 유지되는 두 가지 방식

HTTP는 무상태라 매 요청이 남남입니다. 그래서 매번 '나 아까 그 사람'을 증명해야 하는데, 여기서 갈래가 둘로 나뉩니다.

**세션 — 서버가 기억한다**
서버가 로그인 상태를 자기 저장소에 적어 두고, 브라우저엔 **번호표(세션 ID)** 만 줍니다. 서버가 상태를 쥐고 있어서 **로그아웃·강제 차단을 즉시** 할 수 있습니다. 단점은 서버가 여러 대로 늘면 저장소를 함께 나눠 써야 한다는 것.

**토큰(JWT) — 서버가 기억하지 않는다**
사용자 정보와 만료 시각을 담아 위조 못 하게 **서명한 증명서**를 통째로 내줍니다. 서버는 저장소를 뒤질 필요 없이 서명만 확인하죠. 확장·연동에 강합니다.

여기서 꼭 알아야 할 게 있었습니다.

> **토큰 내용은 암호가 아니라 그냥 인코딩입니다.** 가진 사람은 누구나 열어 봅니다. 서명이 막는 건 '못 바꾸게'이지 '못 보게'가 아닙니다. 그래서 민감정보를 토큰에 넣으면 안 됩니다.

그리고 결론은 명확했습니다 — **이걸 직접 밑바닥부터 만들지 마세요.** MDN조차 "세션 관리를 직접 구현하지 말고 검증된 라이브러리를 쓰라"고 못 박습니다. 제 몫은 "무슨 방식인지 이해하고, 믿을 만한 도구에 맡기는" 판단까지입니다.

### 캐시와 Redis

**캐시**는 자주 쓰는 데이터를 메모리에 잠깐 두는 것 — 매번 창고 깊숙이 다녀오는 대신 자주 찾는 물건을 계산대 옆 바구니에 올려 두는 셈입니다. 속도를 얻는 대신 **원본과 잠깐 어긋날 수 있어서** 수명(TTL)을 정해 둡니다.

로그인에서 캐시가 등장하는 자리가 바로 **세션 저장소**입니다. 세션 확인은 거의 모든 요청마다 일어나 빠름이 생명인데, 키-값 메모리 DB인 **Redis**가 딱 맞습니다. 조회가 매우 빠르고 키마다 **자동 만료(TTL)** 를 걸 수 있어 "30분 활동 없으면 자동 로그아웃"을 손쉽게 만들거든요.

보안 메모 하나 — 브라우저의 `localStorage`는 악성 스크립트(XSS)에 그대로 읽혀 위험하니, OWASP는 자바스크립트가 못 읽는 **httpOnly 쿠키**를 권합니다.

## 10. Little Bobby Tables — SQL 주입

프로그래머 사이의 전설적인 만화(xkcd, 2007)로 배웠습니다. 학교에서 엄마에게 전화가 옵니다.

> **학교:** 아드님 이름을 데이터베이스에 넣었더니 학생 기록이 전부 지워졌어요.
> **엄마:** 아, 우리 아들 이름이 좀 특이하죠. `Robert'); DROP TABLE Students;--` 라서요.
> **엄마:** 앞으로는 입력값을 꼭 소독(검증)하시길 바라요.

아들 이름에 **DB 명령어처럼 생긴 문자**가 들어 있었고, 학교 프로그램이 그걸 이름이 아니라 **명령으로 실행**해서 학생 표를 통째로 삭제한 겁니다. 이것이 **SQL 주입** — 25년 넘게 보안 위협 1위권을 지키는 공격입니다.

### 방어법은 확실합니다

핵심은 하나입니다 — **명령(레시피)과 사용자 입력(재료)을 섞지 않는 것.**

- **위험:** 사용자가 친 글자를 명령 문장에 그대로 이어 붙이기 → DB가 "어디까지가 명령이고 어디부터가 데이터"인지 헷갈림
- **안전:** 자리표(`?`)를 미리 비워 둔 명령을 만들고 입력은 따로 건네기 → DB가 입력을 **무조건 데이터로만** 취급

이 방식을 **파라미터화 쿼리(prepared statement)** 라고 합니다. AI에게 이렇게 요구하면 됩니다.

> "DB에 넣는 값은 문자열로 이어 붙이지 말고, **파라미터화 쿼리**로 처리해줘. 사용자 입력을 그대로 신뢰하지 마."

### 옛날이야기가 아닙니다

2015년 영국 대형 통신사 **TalkTalk**이 이 공격으로 뚫렸습니다. 놀라운 건 공격자가 대단한 조직이 아니라 **모두 21세 미만**이었고, 이용된 구멍은 **3년 반 전에 이미 패치가 나와 있던 것**이었다는 점입니다. 고객 약 15만 7천 명의 정보가 새고 사고 비용은 약 **4,200만 파운드**였습니다.

규제기관의 총평이 짧고 매섭습니다 — **"가장 기본적인 보안 조치조차 하지 않았다."**

2008년 미국 결제회사 Heartland는 같은 공격으로 카드번호 약 1억 3천만 장이 털렸고요. 교훈은 하나였습니다.

> **대부분의 큰 사고는 새로운 마법이 아니라, 오래전에 답이 나온 기본을 안 지켜서 벌어집니다.**

## 11. 개인정보 — 모을수록 무거워진다

이름·이메일·비밀번호 같은 개인정보(PII)가 쌓이면 그건 **자산이자 책임**입니다. 지킬 것 넷을 배웠습니다.

1. **필요한 것만 모은다** — 한국 개인정보보호법도 "목적에 필요한 최소한만"으로 정합니다. "이메일 하나면 되는데 전화번호·생년월일까지 받고 있진 않나?"를 자문할 것.
2. **비밀번호는 절대 그대로 저장하지 않는다** — 그것도 빠른 해시가 아니라 **bcrypt·Argon2** 같은 비밀번호 전용을 씁니다.
3. **민감정보(주민번호·카드번호)는 직접 다루지 않는 게 최선** — 결제는 PG사에, 본인확인은 인증 서비스에 맡깁니다.
4. **밝힌 목적에만 쓴다.**

한 줄 요약이 좋았습니다.

> **덜 모으고, 비밀번호는 해시하고, 민감정보는 남에게 맡기고, 목적 밖으로 쓰지 않는다.**
> 모으지 않은 정보는 유출될 수도 없습니다 — **가장 안전한 데이터는 애초에 안 가진 데이터입니다.**

## 12. 데이터를 잃지 않기 — 백업과 참사들

해커가 없어도 데이터는 사라집니다. **실수 한 번**으로요.

**픽사 「토이 스토리 2」(1998년 제작 중)** — 누군가 잘못된 명령을 실행해 영화 파일이 **눈앞에서 지워지기 시작**했습니다. 설상가상 백업 시스템도 한 달째 고장 나 있었고요. 영화를 살린 건 출산 후 재택근무하던 한 기술 총괄이 **집 컴퓨터에 두었던 2주 전 사본**이었습니다.

**GitLab(2017)** — 엔지니어가 실수로 잘못된 서버의 데이터를 지웠는데, 여러 겹의 백업이 **모두 조용히 고장 나 있어** 6시간치를 잃었습니다.

**Ma.gnolia(2009)** — 백업은 있었지만 **원본과 같은 시스템**에 뒀다가, 그 시스템이 망가지자 백업도 함께 사라져 서비스가 문을 닫았습니다.

### 3-2-1 규칙

백업은 "했다"가 아니라 **"복구된다"** 가 중요합니다. 미국 사이버보안기관(CISA)이 권하는 표준입니다.

- **3벌** — 원본 1 + 사본 2
- **2종** — 서로 다른 매체 두 곳에 (노트북 디스크 + 클라우드)
- **1벌은 다른 장소에** — 화재·도난·랜섬웨어처럼 한 장소를 통째로 잃는 사고 대비

개인이 실천하면 ①노트북 원본 ②외장하드 사본 ③클라우드 한 벌이면 자연스럽게 갖춰집니다.

그리고 CISA가 특히 강조하는 것 — **복구가 진짜 되는지 가끔 확인하세요. 열어본 적 없는 백업은 백업이 아닙니다.**

참고로 클라우드 DB **무료 요금제에는 자동 백업이 없는 경우가 많습니다.** (Supabase 무료는 직접 백업이 필요하고, 자동 일일 백업은 유료 Pro부터입니다.)

## 13. 무료로 시작하기 — DB 고르기

전제가 하나 있었습니다 — **무료 티어는 배우기·MVP용이지, 큰 규모의 운영용이 아닙니다.**

| 서비스 | 종류 | 확인한 점 |
|---|---|---|
| **Supabase** | PostgreSQL | DB 500MB · 스토리지 1GB, **자동 백업 미포함**, 1주 미사용 시 일시정지 |
| **Neon** | PostgreSQL | 개발·프로토타이핑용, 유휴 시 scale-to-zero |
| **Turso** | SQLite | DB 100개 · 5GB, 월 읽기 5억 행 |
| **PlanetScale** | Postgres/Vitess | 시작 요금 월 $5부터 — 무료 후보에서 제외 |

### 내 컴퓨터에 직접 설치하는 길도 있습니다

**SQLite** — DB 전체가 **파일 하나**입니다. 서버를 따로 켤 필요 없이 앱이 그 파일을 직접 읽고 씁니다. 가장 가볍게 시작하기 좋습니다.
**PostgreSQL · MySQL** — 회사들이 실제로 쓰는 오픈소스를 내 컴퓨터에 무료로.
**Docker** — 설치가 번거로우면 명령 한 줄로 띄우고, 필요 없으면 통째로 지웁니다.

흔한 흐름은 이거였습니다 — **로컬에서 만들고 → 세상에 낼 때 클라우드로.**

가입 전 확인할 것 다섯 개도 챙겼습니다: 용량 한도 · 미사용 시 일시정지 · **백업 방법** · 정책 변경 가능성 · 트래픽 증가 시 유료 전환(요금 알림 켜기).

## 14. 실습 — 에이전트로 Todo 앱 만들기

배운 걸 모아 **내 컴퓨터에서 도는 Todo 앱**을 만드는 실습입니다. Todo 앱은 **CRUD의 교과서**라 DB를 손에 익히기에 딱이라고 하네요.

인상적이었던 건 순서입니다. 바로 코드를 시키지 않고 **PRD를 쓴 다음, 구현 전에 DB 구조부터 설계받는 것**이었습니다.

> "위 PRD로 만들 Todo 앱의 **DB 구조(어떤 표·열·관계)를 먼저 설계해서 구조도로 그려 줘.**"

태그 기능을 넣으면 `todos` ↔ `tags`를 잇는 연결표 `todo_tags`가 나오는데, 오늘 배운 **다대다** 그대로입니다. 이 그림을 눈으로 확인하고 넘어가는 거죠.

구현 단계에서 사람이 할 일은 셋이었습니다.

1. **계획 한 번 읽기** (PRD와 맞는지)
2. **위험한 명령은 승인** (이 프로젝트 폴더 안인지 확인)
3. **잘 되던 순간마다 Git 커밋** (되돌릴 지점)

자주 막히는 곳도 미리 알려줬는데, 특히 **"추가했는데 새로고침하면 사라짐"** 은 화면에만 있고 DB엔 안 들어간 것이라는 진단이 유용했습니다. 그리고 **`todo.db`를 GitHub에 올려버림** — 이미 커밋했다면 "git 이력에서도 빼 줘"까지 요구해야 한다는 것도요.

클라우드(Supabase)로 바꿀 때는 **RLS(행 수준 보안)를 반드시 켜야** 합니다. 안 켜면 공개 키로 누구나 데이터에 접근할 수 있습니다.

## 느낀 점

오늘 배운 게 마침 진행 중인 사주타로 프로젝트에 **거의 그대로 들어 있어서** 이해가 빨랐습니다. `readings`와 `share_links` 두 표가 **1:N**(리포트 1건 ↔ 공유 링크 여러 개)이라 `share_links`에 `reading_id` 칸 하나만 있고, `REFERENCES readings(id)`가 강의에서 말한 **키**였습니다. 공유 링크가 리포트 내용을 베끼지 않고 번호로만 가리키는 게 **정규화**였고, 만료 정리용·공유 조회용으로 딱 두 개만 걸어 둔 인덱스가 "자주 쓰는 곳에만 최소한"이라는 원칙 그대로였습니다.

강의에서 배운 개인정보 최소 원칙도 이미 지켜지고 있었습니다. 이름·생년월일은 암호화해서 저장하고, 공유 링크로 나갈 때는 생년월일시를 빼서 내보냅니다. **"가장 안전한 데이터는 애초에 안 가진 데이터"** 라는 문장이, 공유 응답에서 개인 식별 값을 걷어내는 코드와 정확히 같은 이야기였습니다.

반면 **백업은 전혀 안 되어 있다**는 걸 오늘 알았습니다. SQLite 파일 하나에 실제 이용자의 이름·생년월일이 쌓이고 있는데 사본이 한 벌도 없습니다. 3-2-1 규칙에서 3벌·2종·off-site 1벌 중 지켜진 게 없는 셈이죠. 픽사와 GitLab 사고의 공통점이 "있다고 믿었지만 고장 나 있었다"인데, **저는 아예 없는 쪽이라 더 위험합니다.** 정기 사본부터 만들어야겠습니다.

무료 DB 비교에서 Supabase 무료 요금제에 **자동 백업이 없고 1주 미사용 시 일시정지**된다는 점도 눈에 띄었습니다. 클라우드에 올리면 자동으로 안전해질 거라 막연히 생각했는데, 요금제에 따라 **백업은 여전히 내 몫**이라는 걸 확인했습니다.

마지막으로 마이그레이션 경고 — **"칸을 삭제하는 변경은 데이터가 영구히 사라질 수 있으니 구조 변경 전엔 반드시 백업"** 은 앞으로 계속 떠올려야 할 문장입니다. 지금까지 DB 구조를 바꾸는 걸 코드 수정과 같은 무게로 여겼는데, **되돌릴 수 없는 작업**이라는 점에서 성격이 완전히 다르다는 걸 배웠습니다.

오늘은 **지금 매일 쓰는 이 모델이 어디서 왔는지**를 처음부터 따라갔습니다. 그런데 역사 수업으로 끝나지 않았습니다. 마지막엔 제 요금표 앞으로 곧장 내려왔거든요.

시작은 아주 현실적인 곤란이었습니다.

> 80쪽짜리 문서를 통째로 붙여 넣고 "요약해줘"라고 했더니, 앞부분은 잘 반영되는데 **중간이 뭉개지고** 핵심 조항을 슬쩍 빠뜨립니다. 게다가 느리고 비쌉니다. 분명 더 많이 넣었는데 왜 답은 더 나빠질까요.

결론부터 말하면 이렇습니다. **이건 AI가 멍청해서가 아니라, 트랜스포머라는 구조가 원래 그렇게 생겼기 때문입니다.** 그리고 그 구조를 이해하면 "얼마나 넣느냐"가 아니라 **"어떻게 배치하느냐"** 의 문제라는 게 보입니다.

한 줄로 접으면 오늘은 이런 이야기였습니다.

> **이미지 쪽 사람들과 언어 쪽 사람들이 서로 다른 골목에서 각자의 벽에 부딪혔다가, 같은 열쇠 하나로 동시에 벽을 뚫고 한 지점에서 만났다.**

## 1. 이미지가 먼저 연 길 — 은행 창구에서 시작합니다

1990년대 후반, 수표에 손으로 적은 숫자를 기계가 대신 읽게 하려는 시도가 있었습니다. 당시 방식은 이랬습니다. 사람이 먼저 *"숫자의 모서리는 이렇게 생겼다, 곡선은 저렇게 생겼다"* 하고 특징을 손으로 설계해 뽑은 다음, 그걸 분류기에 넘기는 것.

문제는 손글씨가 사람마다 제멋대로라는 점이었습니다. 미리 정해둔 규칙에서 조금만 벗어나면 그냥 무너졌습니다. (어제 배운 개·고양이 규칙 이야기와 똑같은 함정이죠.)

그래서 발상을 뒤집습니다.

> **특징을 사람이 정하지 말고, 픽셀에서 신경망이 스스로 배우게 하자.**

작은 필터를 이미지 위에서 미끄러뜨리며 가장자리·모서리·곡선 같은 국소 무늬를 훑고, **같은 필터를 이미지 전체에 재사용**하는 구조 — 이것이 **CNN(합성곱 신경망)** 입니다. 같은 필터를 돌려 쓰니까 파라미터가 확 줄고, 화면 어느 구석에 있든 같은 무늬를 알아봅니다.

실제로 수표 판독기로 상용화까지 됐습니다. 그런데 **시대를 너무 앞서 있었습니다.** 신경망을 제대로 학습시키려면 방대한 데이터와 계산력이 필요한데 둘 다 턱없이 부족했거든요. 훌륭한 발상은 조용히 서랍으로 들어갔습니다.

### 14년 뒤, 판이 뒤집힙니다

그사이 두 가지가 바뀌었습니다.

1. 인터넷에 쌓인 **라벨 붙은 이미지 수백만 장**과, 그걸로 겨루는 대회(ILSVRC)가 생겼습니다.
2. **게임을 위해 만들어진 GPU**가, 알고 보니 신경망 학습에 필요한 대량 병렬 계산에 완벽하게 들어맞았습니다.

2012년, 한 팀이 이 두 조각을 CNN에 결합해 대회에 나갔습니다.

| | top-5 오류율 |
|---|---|
| 2011년 우승 | 25%대 |
| 2012년 **2위** (기존 방식) | 26.2% |
| 2012년 **우승** (CNN) | **15.3%** |

격차가 10%포인트를 넘었습니다. 해마다 조금씩 깎이던 숫자를 단숨에 무너뜨린 겁니다. **딥러닝 부활의 방아쇠**라고 불리는 그 사건입니다.

승리의 재료가 어제 배운 것들이라 반가웠습니다.

- **ReLU** — 음수면 0, 양수면 그대로. 이 작은 꺾임이 없으면 층을 아무리 쌓아도 전체가 하나의 직선으로 뭉개집니다.
- **dropout** — 학습할 때마다 뉴런 일부를 무작위로 꺼 버립니다. 특정 뉴런 몇 개에 답을 새겨 넣지 못하게 해서, **외우는(과적합) 대신 규칙을 익히게** 만듭니다.
- **GPU 두 장**.

## 2. 그런데 깊게 쌓았더니 더 못해졌습니다

방아쇠가 당겨지자 모두 같은 방향으로 달렸습니다. **더 깊게.** 층이 깊어질수록 낮은 층은 가장자리 같은 단순한 무늬를, 높은 층은 눈·바퀴·얼굴 같은 복잡한 개념을 조합해 알아보니까요.

2014년엔 19층(VGG, 약 7.3%)과 22층(GoogLeNet, 6.7%)이 나왔습니다. 2년 전 15.3%가 절반 이하로 내려왔죠.

그런데 층을 더 얹자 이상한 일이 벌어졌습니다.

> **더 깊은 신경망이 얕은 신경망보다 성적이 나빠졌습니다.**

여기서 중요한 단서. 이건 **과적합이 아니었습니다.** 과적합이라면 훈련 데이터는 잘 맞히고 새 데이터에서만 틀려야 하는데, 이 깊은 망은 **훈련 데이터에서마저 더 못 맞혔습니다.** 학습 자체가 안 된 거죠.

범인은 **vanishing gradient**였습니다.

신경망은 출력에서 생긴 오차를 뒤에서 앞으로 되짚어 보내며 각 층을 고칩니다(역전파). 그런데 이 신호는 층을 하나 통과할 때마다 그 층의 기울기가 곱해지는데, **그 값이 대개 1보다 작습니다.**

> 1보다 작은 값을 수십 번, 수백 번 연달아 곱하면? 순식간에 0에 가까워집니다.

앞쪽 층에는 *"너는 무엇을 얼마나 고쳐야 한다"* 는 지시가 **사실상 도착하지 않았습니다.** 깊이는 축복이 아니라 저주가 됐습니다.

### 지름길 하나로 벽을 뚫다 — ResNet

해법은 놀랄 만큼 간단했습니다.

> 신호가 층을 하나하나 통과하며 약해진다면, **몇 개 층을 건너뛰고 곧장 흐르는 지름길**을 놓아 주면 되지 않을까?

이 지름길을 **skip connection**, 이 구조로 만든 신경망을 **ResNet**이라고 합니다. 사진 분류나 전이학습에서 흔히 쓰는 그 ResNet이 여기서 태어났습니다.

핵심은 **층에게 맡기는 일을 바꾼 것**입니다.

| | 층에게 시키는 일 | 최종 출력 |
|---|---|---|
| 보통 | 입력 x를 받아 원하는 출력 H(x)를 **통째로** 만들어라 | H(x) |
| ResNet | x는 지름길로 흘려보낼 테니, **정답에서 x를 뺀 나머지** F(x)만 만들어라 | **F(x) + x** |

이 "나머지"가 통계에서 말하는 **잔차(residual)** 이고, 그래서 이름이 Res-Net입니다.

왜 이 작은 덧셈 하나가 벽을 뚫을까요. 두 갈래입니다.

**① 학습 신호가 다니는 고속도로가 생깁니다.** 층을 통과할 때는 기울기가 곱해지며 깎이지만, **그대로 더한 통로는 되짚을 때 기울기가 1**입니다. 신호가 깎이지 않고 앞쪽까지 온전히 흘러갑니다.

**② "아무것도 안 하기"가 쉬워집니다.** 필요 없는 층은 입력을 그대로 내보내는 게 최선인데, 여러 비선형 층을 통과시키면서 입력을 조금도 안 바꾸기란 의외로 어렵습니다. 잔차 구조에서는 그냥 **F(x)를 0으로 만들면 출력이 0 + x = x** 가 되어 저절로 됩니다. 필요 없는 층은 조용히 비켜서고, 필요한 층만 일합니다.

결과는 극적이었습니다.

| | top-5 오류율 |
|---|---|
| 사람이 직접 분류 | 약 5% |
| **ResNet (152층, 2015)** | **3.57%** |

여기서 기억할 것은 연도나 이름이 아니라 **문제의 모양**입니다. *긴 사슬을 거치며 신호가 흐려졌고, 사슬을 건너뛰는 통로를 터 주자 뚫렸다.* 곧 언어 쪽에서 똑 닮은 벽을 만나게 되거든요.

## 3. 언어가 부딪힌 또 다른 벽 — 순서의 벽

사진은 한 장이 통째로 주어지지만, 문장은 **단어가 하나씩 순서대로 흐르는 시간의 데이터**입니다. "나는 어제 도서관에서 책을 빌렸다"에서 '빌렸다'는 저 앞의 '나는'과 '책을'을 기억하고 있어야 뜻이 통하죠.

### 먼저, 단어를 숫자로

신경망은 글자를 그대로 못 먹습니다. 그런데 '왕'을 1번, '여왕'을 2번 하는 식으로 번호만 매기면 의미 관계가 통째로 사라집니다.

**word2vec**(2013)의 발상은 단순했습니다.

> **어떤 단어의 뜻은, 그 단어가 어떤 이웃과 함께 등장하는지에 이미 담겨 있다.**

"커피를 ___ 마셨다"의 빈칸을 채우는 연습을 수억 번 시키면, 비슷한 자리에 들어가는 단어들은 자연히 비슷한 벡터를 갖게 됩니다. 누가 뜻을 알려준 적이 없는데도요. 그 공간에서는 **'왕 − 남자 + 여자'를 계산하면 '여왕' 근처**에 도착합니다.

수업에서 직접 돌려본 게 재밌었습니다. '바다'를 기준으로 27개 단어의 유사도를 재 봤는데요.

```
1위 바다 100.0  |  2위 해변 76.7  |  3위 파도 76.5  |  4위 항구 73.3
...
8위 버그 55.2   ←  ???
...
27위 고양이 13.7
```

**'버그'가 8위에 끼어 있습니다.** 뜻으로 보면 커피나 우유보다 바다에서 멀어야 할 것 같은데요. 여기서 핵심이 드러납니다.

> 벡터 공간이 배운 것은 **사전적 정의가 아니라 쓰임의 이웃 관계**입니다.

### RNN — 앞 단어를 기억하며 읽다가

사람이 문장을 읽는 방식을 흉내 낸 것이 **RNN**입니다. 단어를 앞에서 뒤로 하나씩 읽되, 매번 **지금까지 읽은 내용을 요약한 기억**(은닉 상태)을 다음 단어로 넘깁니다.

우아한 발상이었지만 여기서 벽이 드러났습니다. 문장이 길어지면 앞쪽 단어 정보가 은닉 상태를 여러 번 거치는 동안 조금씩 덮이고 흐려져, 뒤에 가서는 거의 남지 않습니다.

그런데 이거, 어디서 본 문제 아닌가요?

> **은닉 상태를 한 단계씩 넘기는 것은, 신경망 층을 하나씩 쌓는 것과 수학적으로 같은 일입니다.**

이미지에서 본 vanishing gradient가 이번엔 깊이가 아니라 **시간 축**을 따라 나타난 것이었습니다. **순서의 벽과 깊이의 벽은 한 뿌리였습니다.**

**LSTM**(1997)이 이 벽을 겨냥합니다. 은닉 상태 옆에 **셀 상태**라는 별도의 장기 기억 통로를 하나 더 두고, 무엇을 기억할지·잊을지·내보낼지를 **게이트**로 조절합니다. 핵심은 이 통로에 **곱셈으로 뒤섞는 변형이 거의 없다**는 점 — ResNet의 지름길과 발상이 놀랍도록 닮았습니다. *통로를 하나 터 주어 신호가 흐려지지 않게 한다.*

다만 **한 단어씩 순서대로 처리한다는 본질은 그대로**였습니다. 앞 단어를 끝내야 뒤 단어를 시작할 수 있으니 **병렬 계산이 불가능**했고, 이 순차성이 두고두고 발목을 잡습니다.

### 문장을 벡터 하나에 욱여넣기 — 고정벡터 병목

번역을 시키려고 나온 구조가 **seq2seq(인코더-디코더)** 입니다.

1. 인코더가 원문을 처음부터 끝까지 읽어, **마지막 은닉 상태 하나**에 문장 전체의 뜻을 압축합니다. (문맥 벡터)
2. 디코더가 그 벡터 **하나만** 받아 번역문을 한 단어씩 풀어냅니다.

원문을 압축했다가 다시 푸는 통역사 구조죠. 그런데 불편한 지점이 있습니다.

> 열 단어짜리 문장이든 쉰 단어짜리 문장이든, **모든 정보가 크기가 고정된 벡터 하나를 반드시 통과해야 합니다.**

이것이 **고정벡터 병목**입니다. 문장이 길어질수록 앞부분이 뭉개졌고, 실제로 번역 품질이 눈에 띄게 무너졌습니다. 통역사에게 **3분짜리 연설을 다 듣고 나서 단 한 문장으로 요약해 전달하라**는 요구와 같습니다. 애초에 무리였죠.

### 되돌아보기로 병목을 깨다 — 어텐션

돌파구는 질문을 바꾸는 데서 나왔습니다.

> 왜 원문 전체를 벡터 하나로 압축해야만 하지? **디코더가 단어를 하나 만들 때마다 원문을 다시 들여다보게** 하면 되지 않나?

이것이 **어텐션(attention)** 입니다. 인코더가 만든 단어별 은닉 상태를 하나로 뭉개지 않고 **전부 남겨 둡니다.** 그리고 디코더는 번역문 단어를 하나 만들 때마다 원문의 모든 단어를 되돌아보며 **지금 이 순간 어느 단어가 중요한지 가중치를 매깁니다.**

'학교'를 번역할 차례면 원문의 'school'에 큰 가중치가 실리는 식이죠. **원문 전체가 매 순간 다시 열람 가능한 참고 자료**가 된 겁니다.

그러자 묘한 질문이 남았습니다. 어텐션은 원래 RNN을 **거들어 주는 보조 장치**였는데, 정작 품질을 끌어올린 주역은 어텐션이었고 RNN의 순차 처리는 걸림돌로 남아 있었습니다.

> **그럼 순차 처리를 거들 게 아니라, 아예 통째로 걷어내고 어텐션 하나만 쓰면 어떨까?**

## 4. 두 길이 트랜스포머에서 만납니다

2017년, 여덟 명의 연구자가 답을 내놨습니다. 논문 제목부터 선언에 가까웠습니다. **"Attention Is All You Need"**.

순환도, 합성곱도 전부 버리고 **오직 어텐션만으로** 문장을 다뤘습니다. 그런데 이 선택이 결정적이었던 이유는 성능보다 먼저 **계산 방식**에 있습니다.

| | 계산 방식 |
|---|---|
| RNN | 세 번째 단어를 처리하려면 두 번째가 끝나기를 **기다려야** 한다 |
| 트랜스포머 | 모든 토큰이 서로를 **동시에** 바라본다 → 한꺼번에 GPU에 올려 **병렬 계산** |

순차의 벽이 사라지자 **더 큰 데이터와 더 큰 모델을 감당할 길**이 열렸습니다. 지금 우리가 LLM이라 부르는 것의 첫 단추가 여기서 끼워집니다.

### Q · K · V — 도서관에서 책 찾기

어텐션은 한 토큰이 다른 토큰들을 둘러보며 *"지금 나를 이해하려면 누구를 참고해야 하는가"* 를 스스로 정하는 방식입니다. 이 저울질을 세 종류의 벡터가 나눠 맡습니다.

| 구성 | 도서관 비유 | 문장 안에서의 역할 |
|---|---|---|
| **Query (Q)** | 내가 들고 온 질문 카드 | "나를 이해하려면 무엇이 필요하지?" |
| **Key (K)** | 책마다 붙은 색인표 | "나는 이런 정보와 관련 있어" |
| **Value (V)** | 실제 책의 내용 | 참고하기로 정한 토큰에서 실제로 가져오는 정보 |

**내 질문 카드(Q)를 서가의 모든 색인표(K)와 맞춰 보고, 잘 맞는 책일수록 그 내용(V)을 많이 가져와 섞습니다.**

그래서 "은행에 예금했다"의 **은행**과 "강가의 은행나무"의 **은행**은 표면은 같지만, 첫 문장에서는 '예금'이, 둘째에서는 '강가·나무'가 강한 단서가 되어 같은 글자를 다른 문맥으로 갈라냅니다.

수식은 한 줄입니다.

```
Attention(Q, K, V) = softmax( QKᵀ / √d_k ) · V
```

한 조각씩 읽으면 이렇습니다.

- **QKᵀ** — 모든 Q와 모든 K를 하나씩 짝지어 맞대 본 **점수표**를 행렬곱 한 번으로 만듭니다.
- **√d_k 로 나누기** — 이게 그냥 숫자 정리가 아니라 재밌었습니다. 벡터가 길어지면 곱해 더하는 항이 늘어 점수가 크게 벌어지는데, **커진 점수는 softmax를 한쪽으로 뾰족하게 몰아붙여 기울기를 0으로 만들고 학습 신호를 끊습니다.** 그래서 **커진 딱 그만큼**(표준편차가 √d_k배 커지니까) 되돌려 눌러 줍니다.
- **softmax** — 점수를 "각 토큰을 얼마나 참고할지"의 비율(합이 1)로 바꿉니다.
- 마지막으로 그 비율대로 **V를 섞어** 문맥이 반영된 새 표현을 만듭니다.

### 여기서 오해 하나를 덜었습니다

강의가 콕 짚어 준 대목입니다.

> **어텐션이 내놓는 것은 "문맥이 반영된 표현의 갱신"이지, 다음 토큰의 확률이 아닙니다.** 다음에 올 토큰의 확률은 그렇게 갱신된 표현을 받아 **맨 끝의 출력층**이 계산합니다.

참고로 디코더는 여기에 **causal mask(인과 마스크)** 를 더합니다. 아직 만들지 않은 미래 위치의 점수를 음의 무한대로 눌러 softmax에서 0으로 만들어, **정답의 미래를 미리 훔쳐보지 못하게** 하는 장치입니다.

### 곁가지 셋 — 나중에 모델 카드에서 만날 것들

**① 멀티헤드 어텐션** — 같은 문장이라도 볼 각도는 하나가 아닙니다. 어떤 시선은 주어와 동사의 짝을, 다른 시선은 괄호 안 예외 문구를, 또 다른 시선은 문체 단서를 봅니다. 이 시선들을 **여러 벌 병렬로 굴리는 것**이 멀티헤드이고, 각각을 **헤드**라고 부릅니다.

**② KV cache** — 답을 한 토큰씩 이어 쓸 때 앞 토큰들의 K·V를 매번 다시 계산하면 낭비라, 보관함에 쌓아 두고 꺼내 씁니다. **문장이 길어질수록 이 보관함의 메모리가 요금과 지연으로 돌아옵니다.** 그래서 설계가 갈립니다.

| 방식 | K·V를 어떻게 나누나 | 특징 |
|---|---|---|
| MHA | Query 헤드마다 자기 몫의 K·V | 표현력 좋음, cache 큼 |
| MQA | 여러 Query 헤드가 **단 하나**의 K·V 공유 | cache 최소, 시야 좁아질 수 있음 |
| **GQA** | 헤드를 묶음으로 나눠 묶음끼리 공유 | 절충안, **요즘 큰 모델들의 선택** |

**③ 위치 인코딩** — 어텐션엔 구멍이 하나 있습니다. Q와 K를 맞대는 계산은 **어느 토큰이 앞이고 뒤인지를 전혀 모릅니다.** "학생이 교사를 칭찬했다"와 "교사가 학생을 칭찬했다"는 똑같은 토큰인데 순서 때문에 뜻이 뒤집히죠. 그래서 위치 정보를 따로 주입합니다.

| 방식 | 직관 |
|---|---|
| Sinusoidal | 위치마다 다른 사인·코사인 패턴을 더함 (원래 방식, 고정) |
| Learned | 위치 번호마다 학습되는 벡터 (학습한 길이 밖은 불확실) |
| **RoPE** | Q·K 벡터를 위치만큼 **회전**시킴 → 절대 위치를 넣는데 **거리 관계가 자연히 반영** |
| **ALiBi** | 멀리 떨어진 토큰일수록 점수에 **거리 비례 감점** → 긴 길이 확장에 유리 |

**어느 방식을 고르느냐가 그 모델이 감당할 수 있는 문장 길이를 가릅니다.** 나중에 "이 모델은 컨텍스트가 왜 이렇게 긴가"의 답이 여기 있습니다.

## 5. 트랜스포머가 세상을 먹다

2017년의 트랜스포머는 사실 **번역기 한 대**에 지나지 않았습니다. 그런데 몇 해 만에 챗봇이자 에이전트의 뼈대가 됐죠. 언어 안에서 세 번의 도약이 있었습니다.

### 도약 ① 사전학습 — 두 갈래로 갈라지다

| | 남긴 쪽 | 훈련 방식 | 잘하는 일 |
|---|---|---|---|
| **BERT** (2018) | 인코더만 | 단어를 가리고 **앞뒤 문맥을 모두 보고** 빈칸 맞히기 | 분류·검색 |
| **GPT** 계열 | 디코더만 | 오직 **다음 토큰 하나** 예측 반복 | 문장 생성 |

둘 다 웹 규모 텍스트로 언어의 통계를 크게 익혀 두고(**사전학습**), 과제마다 적은 데이터로 손보는(**파인튜닝**) 흐름을 공유했습니다. 어제 배운 그 파인튜닝이죠. 그런데 이 "당연함"을 곧 무너뜨리는 반전이 옵니다.

### 도약 ② 스케일링 — 키웠더니 능력이 솟아났다

GPT 계열은 **구조를 바꾸는 대신 그냥 더 키우기로** 합니다. 그러자 질문이 따라왔죠. 얼마나 키우면 얼마나 좋아지는가.

2020년 **스케일링 법칙**이 답했습니다. 모델 크기·데이터·계산량을 키워 가며 재 보니, 틀린 정도(손실)가 어느 순간 뚝 떨어지는 게 아니라 **자원을 몇 배 늘릴 때마다 정해진 비율로 매끈하게** 줄어들었습니다. (이런 관계를 **멱법칙**이라 합니다.)

즉 **성능 향상이 요행이 아니라, 자원을 부으면 예측 가능하게 따라오는 공학의 문제**임이 밝혀진 겁니다.

그래서 GPT-3는 파라미터를 **1,750억 개**까지 밀어붙였습니다. 그런데 놀라운 건 낮아진 손실 수치가 아니라, **아무도 가르치지 않은 능력이 솟아났다**는 점입니다.

> **인컨텍스트 러닝** — 모델의 가중치를 **하나도 바꾸지 않고**, 입력 창 안에 예시 몇 개를 적어 주는 것만으로 새 과제를 수행하는 능력.

이게 왜 사건이냐면, **바로 전까지 당연했던 워크플로가 통째로 뒤집혔기 때문**입니다.

> 과제는 이제 **훈련의 대상이 아니라 프롬프트에 적어 넣는 지시**가 되었습니다. 모델을 다시 학습시키는 대신 **말로 시키면 되는** 시대가 여기서 열립니다.

지금 우리가 프롬프트를 쓰는 방식의 뿌리가 이 창발 능력입니다.

### 도약 ③ 정렬 — 똑똑한데 말귀를 못 알아듣는 모델

여기까지의 모델은 방대한 지식을 품었지만 결정적인 문제가 있었습니다. 훈련받은 목표가 오직 **"다음에 올 법한 토큰을 잇는 것"** 뿐이었다는 사실이죠.

그런데 **"다음에 올 법한"과 "사람이 원하는"은 전혀 같은 말이 아닙니다.**

그래서 사전학습만 마친 모델에게 "프랑스의 수도를 알려 줘"라고 물으면, **답을 아는데도** "이탈리아의 수도도 알려 줘"라고 비슷한 질문을 이어 쓰는 일이 흔했습니다. 인터넷엔 질문 뒤에 질문이 이어지는 텍스트가 널렸으니, 통계적으로 그게 그럴듯한 다음 토큰이었던 겁니다.

이 간극을 메우는 작업이 **정렬**입니다.

| 단계 | 학습 신호 | 파라미터의 무엇이 바뀌나 | 치르는 대가 |
|---|---|---|---|
| 사전학습 | 웹 텍스트의 다음 토큰 | 세계 지식과 언어의 통계 | 막대한 계산량 |
| **지시학습 (SFT)** | 사람이 쓴 모범 답안 | 지식을 꺼내는 **행동 양식** | 모범 답안 작성 비용 |
| **강화학습 (RLHF)** | 답들 사이의 **사람 선호** | 선호하는 쪽으로 분포 이동 | 보상 모델 + 불안정한 RL |
| **직접 최적화 (DPO)** | 답들 사이의 사람 선호 | RLHF와 같으나 절차만 단순 | 선호 데이터 품질 의존 |

**SFT**에서 놓치면 안 되는 것: 이 단계는 **새 지식을 심지 않습니다.** 파리가 프랑스 수도라는 사실은 이미 사전학습에서 파라미터 깊숙이 들어와 있으니까요. SFT가 바꾸는 건 **대화의 매너** — 질문에 질문으로 답하지 말고 지시가 오면 수행하라는 것.

**RLHF**는 영리합니다. 절대 점수를 매기긴 어려워도 **둘 중 나은 쪽을 고르긴 쉽다**는 사람 판단의 결을 이용하죠. 같은 질문에 여러 답을 보여주고 고르게 한 뒤, 그 비교로 **보상 모델**(심판)을 학습시키고 그 점수가 높아지는 쪽으로 밀어붙입니다. 다만 보상만 좇으면 **심판의 허점을 파고드는 답으로 폭주**하니, 원본에서 멀어진 만큼 벌점을 물리는 **KL 제약**으로 고삐를 채웁니다.

효과가 정말 극적이었습니다.

> InstructGPT에서, **130배 넘게 작은 13억 개짜리 정렬 모델**의 답을 **1,750억 개짜리 원본 모델**의 답보다 사람들이 더 선호했습니다.

크기 차이 100배를 **정렬 하나가 뒤집은** 겁니다. 이 사건이 곧이어 등장한 ChatGPT의 바탕이 됐습니다.

**DPO**(2023)는 여기에 우아한 질문을 던집니다. 최종 목표가 선호에 맞는 모델을 얻는 것이라면, 중간의 보상 모델과 불안정한 강화학습을 **건너뛸 수는 없을까?** 답은 "가능하다"였고, 종이 위에서 식을 뒤집으니 **보상 모델이 통째로 사라지고** 이긴 답의 확률은 올리고 진 답은 내리는 손실 하나만 남았습니다.

**정렬의 정체를 한 문장으로 접으면 이렇습니다.**

> **모델이 아는 것은 대체로 사전학습에서 정해지고, 정렬은 그 아는 것을 어떻게 말하고 행동할지를 바꿉니다.** 사실을 새로 심는 단계가 아니라 **태도를 조각하는 단계**입니다.

### 그리고 언어 밖으로

진짜 사건은 그다음이었습니다. 트랜스포머가 언어를 떠나기 시작한 거죠. 이유는 **허무할 만큼 단순**했습니다.

> **어텐션은 애초에 언어에 대한 계산이 아니었습니다.** 조각들이 서로를 둘러보며 누구를 얼마나 참고할지 정하는 것뿐이고, **그 조각이 꼭 단어여야 한다는 조건은 어디에도 없었습니다.**

무엇이든 조각으로 잘라 한 줄로 세울 수만 있다면 픽셀이든 소리든 로봇의 관절 각도든 똑같이 삼킵니다.

| 분야 | 걷어낸 전용 구조 | **무엇을 토큰으로 잘랐나** |
|---|---|---|
| 시각 (**ViT**, 2020) | CNN | 이미지를 16×16 **패치**로 |
| 음성 (**Whisper**, 2022) | 음향 모델 + 발음 사전 + 언어 모델 **조립품** | 오디오 구간의 주파수 그림 |
| 강화학습 (**Decision Transformer**, 2021) | 가치 함수, 정책 경사 | 상태·행동·보상의 **궤적** |
| 이미지 생성 (**DiT**, 2022) | U-Net | 잠재 공간의 패치 |
| 단백질 (**AlphaFold**) | 전용 이론 | 아미노산 서열 |
| 로봇 (**RT-2**) | 전용 제어 | 동작을 **글자 토큰**으로 |

재밌었던 대목 하나. **ViT는 왜 데이터를 그렇게 많이 먹었을까요?**

CNN은 *"가까운 픽셀끼리 관련 있다"*, *"같은 무늬는 어디 있든 같은 무늬다"* 라는 전제를 **구조 자체에 이미 품고** 있습니다. 학습으로 얻은 게 아니라 **설계로 공짜로 얻은 지식**이죠. 트랜스포머엔 그게 없습니다. 모든 패치가 모든 패치를 평등하게 볼 뿐이라, **이웃이 특별하다는 사실마저 데이터에서 배워야** 합니다. 그래서 3억 장 규모로 학습하고 나서야 앞섰습니다.

> **공짜 전제를 버린 대신 전제에 갇히지 않는 자유를 얻은 거래**였고, 데이터가 흔해진 시대엔 그게 남는 장사였습니다.

공식은 어디서나 같았습니다. **그 분야가 오래 붙들던 전용 구조를 걷어내고, 대상을 조각으로 자르고, 조각들이 서로를 참고하게 하는 것.**

### 그래서 활용가에게 좋은 소식

분야마다 각자의 구조를 고집하던 시절이라면 이미지엔 CNN, 음성엔 음향 모델과 발음 사전, 강화학습엔 또 다른 이론 — **입장권이 분야마다 따로** 있었습니다. 지금은 한 구조가 그 자리들을 차지했으니, **구조 하나를 제대로 이해하면 나머지가 대체로 읽힙니다.**

새 모델 이름이 뉴스에 뜰 때마다 처음부터 다시 배우는 대신, 두 질문으로 대개 자리를 잡을 수 있습니다.

> **① 무엇을 토큰으로 잘랐나?  ② 무엇이 무엇을 참고하게 만들었나?**

## 6. 이제 제 요금표 이야기입니다

여기서 강의를 열었던 질문으로 돌아옵니다. **트랜스포머를 그토록 강하게 만든 구조가, 동시에 우리가 매일 치르는 비용과 한계의 정체입니다.**

어텐션은 한 토큰이 **다른 모든 토큰**을 참고하는 방식이라고 했죠. 그 말은 곧 계산량에 대한 이야기이기도 합니다.

> 입력이 토큰 n개면 비교의 수는 대략 **n × n**. 즉 **입력을 두 배로 늘리면 계산은 두 배가 아니라 네 배 가까이** 불어납니다.

긴 입력 = 긴 계산 = **비용과 대기 시간**. 앞서 본 KV cache가 바로 이 비용이 쌓이는 자리입니다.

### 토큰을 직접 세어 봤습니다 — 한국어의 진실

같은 뜻의 문장을 한국어와 영어로 재 봤습니다.

| 문장 | 글자 수 | **토큰 수** | 글자당 토큰 |
|---|---|---|---|
| 계약 기간은 체결일로부터 1년으로 하며, 자동 갱신됩니다. | 32자 | **22토큰** | 1.45 |
| The contract term is one year from the date of execution, with automatic renewal. | 81자 | **16토큰** | 5.06 |

**글자당 토큰이 3.5배 차이 납니다.** 한국어는 글자 하나가 채 한 토큰을 못 가는데, 영어는 다섯 글자가 한 토큰에 들어갑니다.

> 컨텍스트 창이 128K라고 적혀 있어도, **한국어 문서로 채우면 영어보다 훨씬 적게 들어갑니다.** 토큰 단위로 매기는 요금도 같은 비율로 불어나고요.

쪼개진 모양을 보면 더 선명합니다.

```
GPT 방식:      ['계','약',' 기간','은',' 체','결','일','로','부터',' ','1','년','으로',' 하','며',',',' 자동',' �','�','신','됩니다','.']
한국어 모델:    ['계약','기간','##은','체결','##일로','##부터','1','##년','##으로','하','##며',',','자동','갱신','##됩','##니다','.']
```

**'갱'이라는 한 글자가 `�`, `�` 두 조각으로 깨져 있습니다.** 글자를 바이트 단위로 다루다 보니 한글 한 글자가 여러 조각으로 갈라진 거죠. 한국어를 많이 본 토크나이저는 '계약', '기간'처럼 **뜻이 살아 있는 단위**로 자르고 토큰 수도 17개로 더 적습니다.

그리고 이게 **어텐션 비용과 곧장 연결됩니다.** 조각 수가 두 배면 계산은 네 배 가까이. 한국어라서 토큰이 더 나온다는 사실은 요금표 한 줄로 끝나지 않고 **속도와 한계까지 함께 밀어 올립니다.**

### 컨텍스트 윈도우 = 작업대

토큰이 **낱장의 종이**라면, 컨텍스트 윈도우는 그 종이를 **한 번에 펼쳐 놓는 작업대**입니다.

그런데 **책상이 넓다고 검토가 쉬워지지는 않습니다.** 큰 작업대엔 세 문제가 따라옵니다.

1. 자료를 많이 올릴수록 **검토 비용과 시간**이 늘어납니다.
2. **중요한 종이가 어디 있는지 찾기 어려워집니다.**
3. 서로 **충돌하는 자료**를 함께 올리면 어떤 기준을 우선할지 흔들립니다.

> 컨텍스트 윈도우는 **"클수록 좋다"가 아니라, 업무에 필요한 근거를 배치하는 설계 공간**입니다.

### 컨텍스트는 네 칸으로 나눠 설계합니다

```
[역할/목표]      [판단 기준]        [근거 자료]         [출력 형식]
무엇을 하는가     무엇을 우선하나     무엇을 보고 답하나    어떻게 내놓나
```

현장에서 흔한 실패는 **근거 자료만 잔뜩 넣고 판단 기준을 비워 두는 것**입니다.

고객 불만 300건을 넣고 "분석해줘"라고만 하면 모델은 그럴듯한 분류를 만듭니다. 하지만 조직이 원하는 기준이 **환불 위험인지, 법적 리스크인지, 제품 결함인지, 교육 필요인지**를 주지 않으면 그 산출물은 **검토하기가 어렵습니다.**

> 트랜스포머는 문맥을 볼 수 있지만, **여러분의 업무 우선순위를 스스로 책임지지는 않습니다.** 그 우선순위는 컨텍스트 안에 직접 넣어야 합니다.

### 접어 뒀던 곤란의 정체 — Lost in the Middle

자, 이제 강의를 열며 접어 뒀던 그 경험을 펴 볼 차례입니다. 80쪽 문서를 넣었더니 **중간이 뭉개지더라**는 것.

**그건 착각이 아니었습니다.**

> 긴 컨텍스트 연구에서 반복 보고된 결과: 중요한 정보가 입력의 **맨 앞이나 맨 뒤**에 있을 때 성능이 가장 높고, **긴 입력의 중간**에 있을 때 눈에 띄게 떨어지는 **U자 모양 곡선**. 심지어 긴 컨텍스트를 표방하는 모델에서도 나타났습니다.

처방은 논문을 외우는 게 아니라 세 가지를 **습관으로** 만드는 겁니다.

| 처방 | 프롬프트 설계 예 |
|---|---|
| 중요한 기준을 **앞쪽**에 둔다 | "우선순위: 안전, 법규 준수, 비용 순서로 판단합니다." |
| 근거 자료에 **제목과 번호**를 붙인다 | `[자료 A: 2026-05 고객 불만]`, `[자료 B: 내부 정책]` |
| 답변에 **근거 위치**를 요구한다 | "각 결론마다 인용한 자료 번호를 붙이세요." |

> 긴 컨텍스트는 자료를 많이 넣게 해주지만, **자료를 구조화하는 일까지 대신해 주지는 않습니다.**

### 긴 컨텍스트 vs RAG — 무엇이 이기나

"긴 컨텍스트 모델이 나왔으니 RAG는 필요 없어지나요?" 답은 **업무에 따라 다릅니다.**

| 선택 | 어울리는 상황 | 주의할 점 |
|---|---|---|
| **긴 컨텍스트에 직접 넣기** | 자료가 한 번성, 전체 맥락이 중요, 비용 감당 가능 | 길수록 비용·지연·누락 위험 점검 |
| **RAG로 조각만 검색** | 문서가 많고 반복 질의, 최신성·근거 추적 중요 | **검색이 틀리면 좋은 모델도 틀린 근거로 답한다** |
| **요약 후 투입** | 긴 회의록을 여러 단계 판단에 쓸 때 | 요약에서 빠진 정보는 뒤에서 복구 어려움 |

## 7. 실습 — 코드가 아니라 표 두 장

오늘 실습의 산출물이 코드가 아니라 **표 두 장**이었다는 게 인상적이었습니다.

### ① 토큰 예산표

자기 업무 하나를 골라 채웁니다. 숫자가 정확하지 않아도 됩니다. **첫 목표는 비용의 구조를 눈으로 보는 것**이니까요.

| 항목 | 내 업무 값 | 줄일 수 있는가 | 줄이면 위험한가 |
|---|---|---|---|
| 요청 목적 | | | |
| 매번 넣는 고정 지시 | | | |
| 매번 넣는 자료 | | | |
| 사용자가 입력하는 내용 | | | |
| 기대 출력 길이 | | | |
| 하루 예상 호출 횟수 | | | |
| **반드시 남겨야 할 근거** | | | |

그리고 한 문장으로 정리합니다.

> *"이 업무에서 토큰을 줄여도 되는 부분은 ____이고, 줄이면 위험한 부분은 ____입니다. 이유는 ____입니다."*

이 한 문장이 **비용 최적화와 품질 책임을 동시에** 붙잡습니다.

### 병목을 찾는 계산식

```
월간 입력 비용 ≈ 요청당 입력 토큰 × 월 호출 수 × 입력 단가
월간 출력 비용 ≈ 요청당 출력 토큰 × 월 호출 수 × 출력 단가
```

이 식이 유용한 이유는 **가격 숫자를 몰라도 병목의 위치를 찾을 수 있기 때문**입니다.

- 입력은 긴데 출력이 짧다 → **문서 선별·검색·요약 전략**을 본다
- 입력은 짧은데 출력이 길다 → **출력 형식과 상세도 제한**을 본다
- 호출 수가 많다 → **캐시·라우팅·배치 처리** 같은 운영 판단으로

### ② "비용을 줄이자"는 제안을 판단하기

코딩 에이전트가 이렇게 제안했다고 해봅시다.

> *"비용을 줄이려면 고객 상담 로그 원문을 넣지 말고 매번 3줄 요약만 넣으세요. 출력도 5문장으로 제한하면 됩니다."*

겉으로는 맞는 말 같습니다. 하지만 **도메인을 아는 사람이 반드시 물어야 할 질문**이 있습니다.

| 점검 질문 | 왜 묻나 |
|---|---|
| 3줄 요약에서 **법적 리스크 단서**가 빠지지 않는가 | 비용 절감이 책임 문제를 만들 수 있다 |
| 요약을 **누가 만들고 검증**하는가 | 앞 단계 오류가 뒤 단계 답변을 오염시킨다 |
| 5문장이 **의사결정에 충분**한가 | 짧은 답이 검토 가능한 답이라는 보장은 없다 |
| **근거 원문으로 되돌아갈 수** 있는가 | 감사·설명·수정이 필요할 수 있다 |

> **비용 최적화는 "토큰을 줄이기"가 아니라 "위험하지 않은 토큰부터 줄이기"입니다.**

### 에이전트에게 시킬 때의 핵심 한 줄

트랜스포머를 이해한 활용가는 "챗봇 만들어줘"가 아니라 **"컨텍스트가 길어질 때 비용과 누락을 관리하는 구조로 만들어줘"** 라고 시킬 수 있습니다. 그리고 지시에 이 한 줄을 꼭 넣습니다.

> **"구현 코드를 제안하기 전에 설계 판단표를 먼저 보여줘."**

구현에 들어가기 전에 **위험을 먼저 볼 수 있게** 만들기 때문입니다.

### AI가 낸 설계안 체크리스트

| 체크 항목 | 좋은 신호 | 위험 신호 |
|---|---|---|
| 토큰 예산 | 입력·출력·호출 횟수를 나눠 본다 | "긴 컨텍스트 모델 쓰면 됩니다"로 끝난다 |
| 근거 보존 | 결론마다 자료 ID와 문장 번호를 요구한다 | 요약만 남기고 **원문 추적이 없다** |
| 중요 기준 배치 | 판단 기준을 프롬프트 **앞쪽**에 둔다 | 자료 덩어리 뒤에 핵심 지시가 묻힌다 |
| 실패 대응 | 모름·근거 부족·충돌 자료를 처리한다 | **항상 답을 만들도록** 설계한다 |
| 도메인 책임 | 위험한 압축 지점을 **사람이 승인**한다 | 비용 절감 명목으로 핵심 근거를 삭제한다 |

## 8. 오늘을 한 줄로 꿰면

```
CNN과 초기 언어 모델이 각자의 벽에 부딪혔고
    → 그 벽을 넘으려 어텐션이 나왔고
        → 어텐션으로 쌓은 트랜스포머가 거대 언어 모델을 낳았으며
            → 바로 그 어텐션 구조가 토큰과 컨텍스트라는 비용과 한계를 만들었다
```

수식 없이 봤다고 얕게 본 건 아니라는 말이 위로가 됐습니다. 활용가에게 필요한 건 **모델 내부의 모든 계산을 재현하는 것이 아니라, 왜 입력 설계가 답의 품질과 비용을 좌우하는지 설명할 수 있는 것**이니까요.

**어텐션이 왜 토큰 수의 제곱에 가까운 비용을 만드는지, 왜 중요한 정보가 중간에 묻히면 놓치기 쉬운지** 말할 수 있다면 — 그 사람은 코딩 에이전트가 만든 구조를 **판단할 수 있습니다.**

### 활용가가 기억할 한계

| 한계 | 대응 |
|---|---|
| 긴 문서 중 일부를 놓칠 수 있다 | 결론마다 근거 위치를 요구하고 샘플을 검수한다 |
| 토큰 비용이 누적된다 | 입력·출력 예산표를 만들고 반복 지시를 압축한다 |
| 요약이 근거를 삭제할 수 있다 | 위험 정보는 **원문 링크나 ID를 보존**한다 |
| 모델별 토큰화가 다르다 | 쓰는 모델의 공식 문서와 도구로 확인한다 |

그리고 오늘의 마지막 한 문장.

> ### **토큰은 비용을 만들고, 컨텍스트는 한계를 만듭니다.**
> ### **트랜스포머를 잘 쓰는 일은 더 긴 입력을 넣는 일이 아니라, 필요한 문맥을 검토 가능한 구조로 배치하는 일입니다.**

## 9. 오늘의 회고 세 줄

- **머리** — 프롬프트를 "글자를 몇 자 썼나"가 아니라 **"토큰을 몇 개 썼고 어디에 배치했나"** 로 보게 됐습니다. 어텐션이 n×n 비교라는 사실 하나가 "긴 입력이 왜 네 배 비싼가"를 설명해 줍니다.
- **손** — 컨텍스트 설계 캔버스에서 가장 중요한 칸은 **"자료에서 절대 빠지면 안 되는 근거"** 였습니다. 나머지는 다 줄일 수 있지만 그 칸만은 아니니까요.
- **마음** — "비용을 줄이자"는 제안을 받았을 때, **근거 원문으로 되돌아갈 수 있는 길** 하나만은 지키겠다고 마음먹었습니다.

  var box = document.getElementById("ksk-quiz");
  if (!box) return;

  function render() {
    box.innerHTML = "";
    var done = 0, correct = 0;

    QUIZ.forEach(function (item, qi) {
      var card = document.createElement("div");
      card.className = "ksk-q";

      var h = document.createElement("h4");
      h.innerHTML = "<span>Q" + (qi + 1) + ".</span> " + item.q;
      card.appendChild(h);

      var buttons = [];
      item.a.forEach(function (text, ai) {
        var btn = document.createElement("button");
        btn.type = "button";
        btn.className = "ksk-opt";
        btn.textContent = "①②③④".charAt(ai) + " " + text;
        btn.addEventListener("click", function () {
          if (card.dataset.answered) return;      // 한 문제는 한 번만
          card.dataset.answered = "1";
          done++;
          if (ai === item.c) correct++;

          buttons.forEach(function (b, bi) {
            b.disabled = true;
            if (bi === item.c) b.classList.add("ok");
            else if (bi === ai) b.classList.add("no");
          });

          var exp = document.createElement("div");
          exp.className = "ksk-exp";
          exp.innerHTML = (ai === item.c ? "✅ <b>정답입니다.</b> " : "❌ <b>아쉽네요.</b> 정답은 "
                           + "①②③④".charAt(item.c) + " 입니다. ") + item.e;
          card.appendChild(exp);

          showScore(done, correct);
        });
        buttons.push(btn);
        card.appendChild(btn);
      });

      box.appendChild(card);
    });

    var score = document.createElement("div");
    score.className = "ksk-score";
    score.id = "ksk-score";
    score.style.display = "none";
    box.appendChild(score);

    function showScore(d, c) {
      var pct = Math.round(c / QUIZ.length * 100);
      var msg;
      if (d < QUIZ.length) {
        msg = "지금까지 <b>" + d + "문제</b> 중 <b>" + c + "개</b> 맞혔습니다. 남은 문제 "
              + (QUIZ.length - d) + "개!";
        score.innerHTML = msg + '<div class="ksk-bar"><i style="width:' + (d / QUIZ.length * 100) + '%"></i></div>';
      } else {
        if (pct === 100)     msg = "완벽합니다. 오늘 강의를 제대로 가져가셨네요.";
        else if (pct >= 80)  msg = "훌륭합니다. 핵심은 다 잡으셨습니다.";
        else if (pct >= 60)  msg = "절반 넘게 맞히셨습니다. 틀린 문제 해설만 다시 읽어보세요.";
        else                 msg = "본문을 한 번 더 훑고 다시 풀어보시길 권합니다.";
        score.innerHTML = '<span class="n">' + c + " / " + QUIZ.length + "</span>"
          + "정답률 <b>" + pct + "%</b><br>" + msg
          + '<div class="ksk-bar"><i style="width:' + pct + '%"></i></div>';
        var again = document.createElement("button");
        again.type = "button";
        again.className = "ksk-again";
        again.textContent = "↻ 다시 풀기";
        again.addEventListener("click", render);
        score.appendChild(again);
      }
      score.style.display = "block";
    }
  }

  render();
})();

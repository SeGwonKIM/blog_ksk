모두의연구소 "바이브 코딩으로 웹 만들기" 과정 3강 "오늘 써볼 프레임워크는?"의 세부 스텝 여섯 개를 정리합니다. 프레임워크가 왜 이렇게 많이 생겼는지에서 시작해, AI와 대화하며 PRD를 만드는 법, 그리고 프론트엔드가 백엔드·API와 데이터를 주고받는 원리까지 하루 안에 쭉 이어지는 흐름이었습니다.

## 1. 프레임워크는 왜 이렇게 많을까

React, Vue, Svelte, Angular, Solid, Qwik에 Next.js, Nuxt, SvelteKit 같은 메타프레임워크까지 검색하면 검색창에서부터 길을 잃기 쉽습니다. 오늘의 답은 "다 몰라도 됩니다"였지만, 막연한 위로가 아니라 **왜 이런 도구가 생겼는지**를 알아야 AI의 추천도 판단할 수 있다는 전제가 붙습니다.

프레임워크(framework)는 직역하면 '뼈대'입니다. 집을 지을 때 기둥·배관을 매번 0부터 설계하지 않고 검증된 골조 위에 올리듯, 웹서비스에서 반복되는 일을 미리 정리해 둔 것이 프레임워크입니다. **라이브러리**가 필요할 때 꺼내 쓰는 부품 상자라면, 프레임워크는 "이 안에서는 이렇게 짜자"는 약속까지 함께 주는 **제어의 역전(Inversion of Control)** — 전체 흐름을 프레임워크가 쥐고 있다가 정해진 순간에 내 코드를 불러주는 방식입니다. 오늘의 산출물은 코드가 아니라, "내 조건에서 어떤 프레임워크가 맞는지" AI에게 제대로 물을 수 있는 **선택 프롬프트와 평가표**였습니다.

## 2. 프레임워크가 실제로 푸는 세 가지 문제 — 반복, 변화, 연결

순수 HTML/CSS/JS로는 화면이 커질수록 같은 문제가 반복됩니다. 전문가 카드 30개를 복사해두면 배지 디자인 하나 바꿀 때 30곳을 다 고쳐야 하는 식입니다. 개발자들은 이 문제를 세 이름으로 부릅니다.

- **컴포넌트(component)**: 재사용 가능한 화면 조각. 설계를 한 곳에 두고 데이터만 바꿔 여러 번 불러 씁니다.
- **상태(state)**: 화면의 현재값. 필터를 하나 바꾸면 목록·개수·안내 문구·페이지 제목까지 여러 곳이 함께 바뀌어야 하는데, 상태 하나를 중심에 두면 나머지는 자동으로 파생됩니다.
- **라우팅(routing)**: 주소(URL)에 따라 어떤 화면을 보여줄지 정하는 길 안내입니다.

React가 이걸 처리하는 방식이 **가상 DOM(Virtual DOM)**입니다. 벽을 하나하나 직접 칠하는 대신, 리모델링 후 모습을 설계도에 먼저 그리고 지금 집과 비교해 **바뀐 부분만** 칠하는 것과 같습니다(재조정, reconciliation). 이 모든 건 컴퓨터과학의 오래된 두 원칙 — 복잡한 속을 감추는 **추상화**와, 바뀌어야 할 이유가 같은 것끼리 조각내는 **모듈화**(1972년 데이비드 파나스)의 실제 사례이기도 합니다. 프레임워크의 역사도 결국 이 문제를 푸는 계보였습니다: 2006년 jQuery(브라우저 호환성) → 2010년 AngularJS·Backbone(화면 구조화) → 2013년 React(컴포넌트·선언형 UI) → 2014년 Vue(점진적 도입) → 2016년~ Svelte·Solid·Qwik(각자 다른 병목 최적화).

## 3. 그래서 어떤 프레임워크를 고르나 — AI 시대의 선택 기준

문법은 이제 AI가 짜줍니다. 그런데 오히려 "무엇을 고르냐"가 더 중요해진 이유는, AI가 프레임워크마다 코드를 짜는 **정확도가 다르기** 때문입니다. DesignBench 벤치마크에서 React·Vue는 컴파일 성공률 0.83을 넘겼지만 Angular는 0.69~0.76에 그쳤습니다 — 학습 데이터가 많고 규칙이 일관된 프레임워크일수록 AI가 더 정확하게 짭니다.

Stack Overflow 2025 설문에서 React 사용률은 44.7%로 1위지만, 개발자 만족도는 오히려 Svelte가 가장 높았습니다(약 74%, React는 62%). **"많이 쓴다"와 "내 조건에 맞다"는 다른 질문**이라는 걸 다시 확인한 셈입니다. 그래서 오늘 배운 판단 축은 다섯 가지였습니다: AI 친화도, 러닝커브, 생태계, 일자리·자료, 장기 유지보수. 정답 하나를 찾기보다 후보를 2~3개로 좁히고 근거를 비교하는 게 현실적인 접근입니다.

## 4. AI와 함께 PRD 만들기

"○○ 만들어 줘" 한 방으로 시작하지 않고, AI와 **주고받으며** 정하는 3단계 대화법을 배웠습니다.

1. **인터뷰**: "구체적인 PRD를 짜기 위해 정해야 할 것들을 한 번에 하나씩 물어봐 줘"라고 요청해 AI가 되묻게 만듭니다.
2. **추천**: 윤곽이 잡히면 "어떤 프레임워크가 좋을지 3개 이상 장단점과 함께 추천해 줘" — 그리고 왜 그걸 추천했는지 한 번 더 되묻습니다.
3. **정리**: "지금까지 정한 내용을 PRD로 작성해 줘"로 대화를 문서로 남깁니다.

이 PRD가 오늘 과제의 뼈대이자, 나중에 백엔드 기능을 붙여 나갈 때의 길잡이가 됩니다.

## 5. 백엔드 없이 프론트엔드 먼저 만들기 — 목업 데이터

프론트엔드(홀)와 백엔드(주방) 비유가 인상적이었습니다. 백엔드 API가 아직 없어도, **목업 데이터(mock data)** — 진짜 API가 보내줄 것과 같은 구조의 가짜 데이터 — 를 코드에 미리 넣어두면 화면을 먼저 완성하고 테스트할 수 있습니다. 실무에서는 이걸 **병렬 개발**이라 부르며, 프론트엔드·백엔드 팀이 동시에 일하는 기본 방식입니다.

핵심은 **교체가 쉬운 구조**를 만드는 것이었습니다. 데이터를 컴포넌트 안에 직접 박아 넣으면 나중에 API로 바꿀 때 컴포넌트마다 뒤져야 하지만, `mockData.js`처럼 별도 파일로 빼두면 `import` 한 줄만 `fetch` 호출로 바꾸면 끝입니다 — 지난 시간에 배운 **관심사의 분리**가 실전에 그대로 적용되는 지점입니다.

## 6. API가 실제로 하는 일 — REST와 GraphQL

API는 프로그램끼리 대화하는 창구(서빙 창구)이고, 오갈 때 쓰는 공통 형식이 **JSON**입니다. 오늘 가장 널리 쓰이는 방식인 **REST API**는 HTTP의 네 동사를 데이터 조작에 대응시킵니다.

| 동사 | 식당 비유 | 의미 |
|---|---|---|
| GET | "메뉴판 보여줘" | 목록을 가져옴 |
| POST | "이거 주문할게" | 새 데이터 생성 |
| PUT | "1번 주문 이렇게 바꿔줘" | 기존 데이터 수정 |
| DELETE | "1번 주문 취소" | 데이터 삭제 |

**GraphQL**은 "필요한 필드만 골라서 달라"는 방식으로 REST보다 통신은 가벼워지지만 백엔드 구조는 더 복잡해집니다. API 형식도 역사를 거쳐 왔습니다: RPC(1980년대, 원격 함수 호출) → SOAP(1990년대, XML 규격) → REST(2000년대, 지금의 표준) → GraphQL(2015년, Meta). JSON이 XML을 이긴 이유도 결국 "가벼움과 단순함"이었습니다. 첫 프로토타입은 자료가 많고 AI가 익숙한 **REST가 기본**이라는 정리로 마무리됐습니다.

## 느낀 점

오늘 가장 크게 바뀐 생각은 "프레임워크를 고르는 문제"가 문법 암기가 아니라 **판단력의 문제**라는 점입니다. React든 Vue든 코드는 AI가 짜주지만, 내 서비스가 반복·상태·연결 중 어디에서 부담이 큰지, 팀 규모와 유지보수 기간이 어떤지는 결국 내가 설명해야 AI의 추천을 검증할 수 있습니다. 그리고 PRD 3단계 대화법(인터뷰→추천→정리)은 오늘부터 바로 써먹을 수 있는 도구라, 다음에 새 프로젝트를 시작할 때는 코드부터 짜지 않고 이 순서를 먼저 밟아볼 생각입니다. 목업 데이터와 REST API 부분은 지금까지 만든 게임들이 전부 프론트엔드 단독이었다는 걸 새삼 깨닫게 해줬습니다 — 다음 단계는 진짜 백엔드를 붙여보는 것이 되지 않을까 싶습니다.

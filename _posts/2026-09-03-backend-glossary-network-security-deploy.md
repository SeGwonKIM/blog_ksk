> 🗓️ **자료 생성일: 2026-09-03 · 게시일: 2026-09-03**

모두의연구소 "바이브 코딩으로 웹 만들기" 과정 4강 "백엔드 — 화면 뒤에서 일어나는 일들"을 정리합니다. 지금까지 만든 건 **손님 눈에 보이는 홀**이었고, 오늘 배운 말들은 전부 **눈에 안 보이는 주방**에 관한 것이었습니다. 용어가 많아 보이지만 결국 하루가 하나의 질문으로 이어집니다 — "왜 내가 만든 화면은 친구가 못 열까?"

시작은 아주 익숙한 장면이었습니다. 밤새 화면을 만들어 친구에게 `http://localhost:3000`을 보냈는데 "이 사이트에 연결할 수 없음"이 뜨고, 아침에 노트북을 다시 켜니 입력해 둔 내용이 싹 사라져 있습니다. 증상은 셋인데 원인은 하나였습니다 — **지금까지 만든 것은 내 컴퓨터 안에만 있고, 세상과 연결된 뒤편이 없다.**

## 요청 한 번의 여정

용어를 하나씩 보기 전에, 주소창에 엔터를 누른 1초 안에 벌어지는 일부터 보면 나머지가 전부 이 여정 위의 한 지점이 됩니다.

1. 브라우저가 **DNS**에 묻는다 — "mysite.com이 어디죠?"
2. 받은 **IP**의 **443번 포트**로, **HTTPS** 자물쇠를 걸고 연결한다
3. **HTTP**로 "이 페이지 줘"라고 요청하면 서버가 화면·데이터를 응답한다
4. 브라우저가 그 응답을 화면으로 그린다

이 왕복이 페이지를 넘길 때마다 반복되고, **백엔드는 이 왕복의 반대편 끝에서 대답하는 쪽**입니다. 지난 시간에 쓴 목업 데이터는 이 여정 없이 화면 안에 미리 넣어 둔 것이었죠.

## 1. 뒤편이 있다 — 백엔드와 클라이언트-서버

식당으로 바꾸면 한눈에 들어옵니다. **클라이언트**(내 브라우저·앱)는 주문하러 왔다 가는 손님이고, **서버**는 늘 그 자리에 켜져 있는 24시간 주방 겸 창고입니다. 그래서 웹서비스는 손님 눈에 보이는 **홀(프론트엔드)** 과 눈에 안 보이는 **주방(백엔드)** 으로 나뉩니다. `localhost`는 "지금 이 컴퓨터"만 가리키는 특별한 주소라, 친구가 자기 컴퓨터에서 열면 '친구 자기 컴퓨터의 3000번'을 찾게 되고 거기엔 아무것도 없었던 겁니다.

오늘 가장 실용적인 수확은 **판단 기준**이었습니다. 여러 사람이 나눠 쓰거나 · 껐다 켜도 남아야 하거나 · 비밀이 오가면 → 서버가 필요합니다. 반대로 내 화면 안에서 잠깐 보이고 마는 것(색 바꾸기, 애니메이션)은 서버 없이도 됩니다.

## 2. 주소가 화면이 되기까지

### 도메인과 DNS

인터넷의 모든 컴퓨터에는 `142.250.72.14` 같은 번호(IP 주소)가 있는데 외우고 관리하기가 불편합니다. **도메인**은 사람이 외우는 가게 이름이고, **DNS**는 그 이름을 번호로 바꿔 주는 전화번호부입니다.

도메인을 '외우기 편한 별명'으로만 알면 절반만 아는 것이라는 설명이 좋았습니다. 진짜 힘은 **이름과 실제 서버 사이에 한 겹을 두는 것** — 앞은 그대로 두고 뒤를 얼마든지 바꿀 수 있습니다. 가게가 이사를 가도 상호는 그대로라 단골은 상호만 기억하면 되는 것과 같죠. 지난 시간에 배운 **추상화**가 여기서 또 나옵니다.

흔한 함정 두 가지도 함께 배웠습니다. 하나는 "방금 바꿨는데 왜 안 바뀌지?" — DNS는 답을 한동안 캐시하기 때문에 전 세계로 퍼지는 데(전파) 몇 분에서 몇 시간이 걸립니다. 다른 하나는 자물쇠에 대한 오해인데, HTTPS 자물쇠는 **'믿을 만한 회사'라는 증명이 아니라** '이 도메인의 주인과 암호를 걸어 통신 중'이라는 뜻일 뿐이라 **피싱 사이트도 자물쇠를 붙일 수 있습니다.** 자물쇠 유무보다 도메인 철자를 봐야 합니다.

### IP, 포트, 방화벽

IP가 '건물 주소'라면 **포트**는 그 건물 안의 '호실 번호'입니다. 컴퓨터 한 대에 문이 0~65535번까지 있고, 웹은 보통 80번(HTTP)과 443번(HTTPS)을 씁니다. 개발 중 자주 보는 `localhost:3000`의 그 3000이 포트 번호였습니다. **방화벽**은 그 문을 지키는 경비라 필요 없는 문은 닫아 둡니다.

여기에 **내부망과 외부망**이 겹칩니다. 집이나 회사 안은 `192.168.0.5` 같은 사설 IP를 쓰는 내부망이고, 그 바깥이 외부망(곧 인터넷)입니다. 둘 사이의 문지기가 공유기(**NAT**)인데 안에서 밖으로는 자유롭지만 밖에서 안으로는 기본적으로 못 들어옵니다 — 그래서 평소엔 안전하고, 그래서 내 `localhost:3000`이 나한테만 보였던 겁니다.

### HTTP, HTTPS, TLS

**HTTP**는 "이 페이지 줘"(요청)와 "여기 있어"(응답)로 오가는 공통 언어이고, **HTTPS**는 그 대화를 암호로 감싼 안전한 버전입니다. HTTP가 엽서라면 HTTPS는 밀봉된 봉투입니다.

원리는 **열쇠가 두 개**라는 발상이었습니다. **공개키**는 누구나 편지를 넣을 수 있는 우편함 투입구라 공개해도 되고, **개인키**는 그걸 여는 유일한 열쇠라 서버만 갖습니다. 누구나 잠글 수는 있지만 열 수 있는 건 서버뿐이죠. 실제로는 접속 초반에 공개키로 '오늘만 쓸 임시 열쇠'를 주고받고 그다음부터 빠른 방식으로 대화하는데, 이 첫 인사가 **TLS 핸드셰이크**입니다. 그 사이트가 진짜인지는 **인증기관(CA)** 이 서명한 인증서로 보증하고요. 다행히 이 과정은 배포 플랫폼이 자동으로 해 줍니다.

### 패킷과 TCP/IP

사진 한 장을 보낼 때 통째로 건너가지 않습니다. 데이터는 작은 조각(**패킷**)으로 쪼개져 각자 여행한 뒤 도착지에서 재조립됩니다. 비유 셋이 명쾌했습니다 — 긴 편지를 인덱스카드 여러 장에 번호를 붙여 보내는 **우편**, 통째로 보내다 떨어뜨리면 다 망하지만 조각으로 나누면 한 조각만 다시 보내면 되는 **피자**, 한 길이 막히면 우회하는 **내비**. 이렇게 쪼개고·주소 붙이고·순서 맞추는 공통 규칙이 **TCP/IP**입니다.

### HTTP 상태 코드 — 인터넷의 신호등

서버가 응답할 때 함께 보내는 세 자리 숫자입니다. 수백 개를 외울 필요 없이 **맨 앞 숫자만** 보면 됩니다.

| 앞자리 | 뜻 | 신호등 |
|---|---|---|
| 2xx | 성공 | 초록불, 통과 |
| 3xx | 다른 데로 | 우회 (주소가 옮겨졌을 때) |
| 4xx | 요청(나)의 잘못 | 주소를 틀렸거나 권한이 없음 |
| 5xx | 서버의 잘못 | 서버가 터짐 |

자주 만나는 것들은 이렇습니다.

| 코드 | 뜻 | 한마디로 |
|---|---|---|
| 200 | 성공 | "다 잘됐어" — 잘 되면 눈에 안 보이는 코드 |
| 301 / 302 | 주소 이동 | "그 페이지 저쪽으로 옮겼어" |
| 401 | 로그인 필요 | "누구세요?" |
| 403 | 권한 없음 | "누군지 알지만, 넌 안 돼" |
| 404 | 없는 페이지 | "그런 페이지 없어" |
| 429 | 너무 많은 요청 | "천천히 좀" |
| 500 | 서버 오류 | "네 잘못 아냐, 내가 터졌어" |

**4면 내 잘못, 5면 서버 잘못**만 알아도 절반은 맞힙니다. 실전 팁으로, AI에게 도움을 청할 땐 화면의 에러를 그대로 붙여 주면 원인을 훨씬 잘 찾아 준다고 합니다. 브라우저에서 마우스 오른쪽 → 검사 → 네트워크 탭을 열고 새로고침하면 이 숫자들이 실제로 보입니다. (덧: `418 I'm a teapot`은 1998년 만우절 농담으로 만든 코드로 "나는 찻주전자라서 커피를 못 내려"라는 뜻이라고.)

## 3. 주방 안에서 — 백엔드가 실제로 하는 일

백엔드가 하는 일은 한 문장이면 충분합니다 — **요청을 받아서, 처리하고, 응답을 돌려준다.** 홀에서 주문서(요청)를 받고, 레시피(비즈니스 로직)대로 조리하고, 창고(데이터베이스)에서 재료를 꺼내 완성한 요리를 내보냅니다.

### 엔드포인트와 API

백엔드는 통째로 열려 있지 않고 정해진 몇 개의 **창구(엔드포인트)** 만 프론트에 열어 줍니다. 창구 하나는 "주소(URL) + 동작"의 조합이고 그게 곧 하나의 기능입니다.

```
GET  /products   → "상품 목록 주세요"
POST /login      → "이 정보로 로그인 처리해 주세요"
```

이렇게 공개한 창구들의 묶음이 **API**입니다. 잘 짜는 관례(REST)의 핵심은 **주소는 '무엇'(명사), 동작은 메서드로** — 그래서 `/getProducts`(동사)가 아니라 `/products`(명사)로 씁니다. 비전공자에게 필요한 건 완벽한 설계가 아니라 "내 서비스엔 어떤 창구가 필요하지?"를 그려 보는 판단이라는 말이 인상적이었습니다.

### CRUD와 JSON

대부분의 서비스가 데이터에 대해 하는 일은 사실상 넷뿐입니다 — 만들기(Create)·읽기(Read)·고치기(Update)·지우기(Delete), 줄여서 **CRUD**. 인스타그램의 게시물 올리기·보기·수정·삭제나 쇼핑몰의 상품 등록·조회·수정·삭제처럼 겉모습만 다를 뿐 속은 전부 이 네 동작의 반복입니다.

프론트와 백엔드가 데이터를 주고받을 때 쓰는 공용어는 **JSON**입니다. '이름표: 값' 쌍으로 적는 가벼운 텍스트죠.

```json
{ "name": "홍길동", "age": 30, "isMember": true }
```

사람이 읽기 쉬운 텍스트인 데다 언어를 가리지 않아서 사실상 표준이 됐습니다.

### 백엔드의 진짜 가치 — "프론트는 못 믿는다"

가장 중요한 보안 원칙은 이것이었습니다. **가격·수량·권한 같은 검증은 반드시 백엔드에서 다시 해야 합니다.** 프론트는 사용자의 컴퓨터에서 돌아가므로 얼마든지 조작할 수 있기 때문입니다. 화면에 "가격 10,000원"이라고 떠 있어도 악의적 사용자는 그 값을 100원으로 바꿔 주문 요청을 보낼 수 있습니다. 프론트의 검증은 사용자 편의를 위한 것이고, **진짜 방어선은 언제나 백엔드**입니다.

## 4. 안전하게 만들기 — AI가 약한 곳

오늘 가장 뼈아픈 통계는 이것이었습니다. 보안 회사 Veracode가 100개 넘는 AI 모델로 실험했더니 **AI가 생성한 코드의 약 45%에 보안 결함**이 있었고, 모델이 더 똑똑해져도 이 비율은 거의 줄지 않았습니다. 문법은 좋아졌지만 안전은 그대로였다는 뜻입니다. AI는 "돌아가는 코드"는 잘 만들지만 "안전하고 튼튼한 코드"는 놓칩니다 — **명시적으로 요구하지 않으면 보안을 알아서 챙기지 않기 때문**입니다.

### 인증 vs 인가

로그인 기능에는 사실 두 단계가 숨어 있습니다. 콘서트장으로 비유하면 딱 맞습니다.

| 단계 | 비유 | 질문 | 실패하면 |
|---|---|---|---|
| **인증**(Authentication) | 입구의 표 검사원 | "당신, 표 주인 맞아요?" | 401 "누구세요?" |
| **인가**(Authorization) | VIP 구역의 바운서 | "이 방에 들어갈 권한은 있어요?" | 403 "넌 안 돼" |

로그인에 성공하면 서버가 **토큰**을 주는데, 클럽 입구에서 받는 손목 밴드 같은 것이라 이후엔 매번 신분증을 안 보여줘도 밴드만 보이면 통과됩니다. AI가 이 로직을 만들어 주지만 "내 데이터를 남이 보면 안 되는데, 권한 확인(인가)이 되어 있나?"는 꼭 되물어야 합니다.

### 환경변수 — 비밀은 코드에 적지 않는다

한 개발자가 급한 마음에 API 키를 코드에 적어 GitHub에 올렸는데, 몇 분 만에 봇이 그 키를 발견해 훔쳐 갔고 클라우드에서 비싼 작업을 잔뜩 돌려 며칠 뒤 수백만 원짜리 청구서가 날아왔다는 이야기가 나왔습니다. 과장이 아니라, GitGuardian 집계로 **2025년 한 해 공개 GitHub에 유출된 비밀키·비밀번호가 약 2,865만 개**(전년 대비 34% 증가)였고 **AI 서비스 키 유출은 1년 새 81% 급증**했습니다.

```
나쁜 예:  apiKey = "sk-a1b2c3d4e5f6..."   ← 올라가는 순간 유출
좋은 예:  apiKey = 환경변수에서 불러오기      ← 실제 값은 코드 밖 .env 파일에
         (그리고 .env는 .gitignore로 막아 깃에 안 올라가게)
```

AI에게는 이렇게 말하면 됩니다 — **"API 키와 DB 접속 정보는 코드에 넣지 말고 환경변수로 빼줘. .env 파일은 깃에 안 올라가게 해줘."** 한 줄 요약은 **코드 = 공개해도 되는 것 / 환경변수 = 절대 공개하면 안 되는 것**입니다.

### 해시, 솔트, bcrypt

비밀번호는 절대 그대로 저장하면 안 됩니다. **해시**는 비밀번호를 되돌릴 수 없는 '지문'으로 바꿉니다 — 달걀을 프라이로 만들 수는 있어도 프라이를 다시 달걀로 되돌릴 수 없듯이요. 그런데 흔히 쓰는 비밀번호(`123456`)는 지문도 뻔하니, **솔트**(사람마다 다른 무작위 값)를 섞어 지문을 냅니다. 그리고 **bcrypt** 같은 일부러 느리게 계산되는 방식을 쓰는데, 느린 게 장점입니다 — 도둑이 수억 개를 대입해 보기 어려워지니까요.

역사에 남은 유출 사고들도 함께 봤습니다. 에퀴팩스(2017, 알려진 취약점 방치로 1억 4,300만 명), 소니 PSN(2011, 7,700만 명), 야후 보이스(2012, **평문 저장**), 마이스페이스(2008, 3억 6천만 계정), MOVEit(2023, 9천만 명 이상). 공통점은 전부 **막을 수 있었던 것들**이었다는 점입니다.

### 쿠키와 세션

웹은 원래 기억력이 없습니다. 초창기 HTTP는 요청 하나하나를 매번 처음 보는 손님처럼 취급했고(**무상태**), 그대로라면 로그인하고 다음 페이지로 가는 순간 로그아웃될 겁니다. 이 건망증을 고치려고 나온 것이 쿠키와 세션입니다.

**쿠키**는 내 지갑 속 작은 카드이고(사이트가 적어 준 번호), **세션**은 사이트 금고 속 내 서류철입니다. 로그인하면 서버가 세션을 만들어 고유 번호를 발급하고 → 그 번호를 쿠키로 브라우저에 주고 → 이후 요청마다 브라우저가 쿠키를 함께 보내고 → 서버가 번호로 나를 알아봅니다. **진짜 정보를 쿠키에 두면 안 되는** 이유도 명확했습니다. 쿠키는 사용자가 조작할 수 있어서 `이름=일반사용자`를 `이름=관리자`로 바꾸는 장난이 가능하거든요.

### RLS — Supabase를 쓴다면

Supabase는 **브라우저가 공개 키로 DB에 직접 접근하는 구조**라 **RLS(행 수준 보안)** 를 켜고 규칙을 짜야만 안전합니다. 안 켜면 그 공개 키로 누구나 데이터를 읽고 고치고 지울 수 있습니다. 특히 AI 코딩 툴로 만든 테이블은 **RLS가 꺼진 채 시작되는 경우가 많아** 실제로 수백 개 앱이 데이터를 통째로 노출한 사고(CVE-2025-48757)가 있었습니다. 공식처럼 외울 것 — **공개 키 + RLS 켜짐 = 안전 / RLS 꺼짐 = 열린 DB.**

## 5. 세상에 내보내기

### 배포

**배포**는 내 컴퓨터에만 있던 서비스를 늘 켜진 서버에 올려 누구나 주소로 들어올 수 있게 하는 것입니다. 현대 웹서비스는 보통 셋으로 나눠 올립니다 — 각자 잘하는 게 다르기 때문입니다.

| 무엇을 | 어디에 | 식당 비유 |
|---|---|---|
| 화면(프론트) | Vercel · Netlify | 전 세계 여러 지점의 홀 — 손님 가까운 곳에서 빠르게 |
| 서버(백엔드) | Render · Railway | 늘 켜진 주방 — 요청을 계속 처리해야 |
| 데이터(DB) | Supabase 등 관리형 | 재료 창고 — 안전하게 보관해야 |

요즘 배포는 GitHub에 올리면 자동으로 되는 흐름입니다. 코드를 GitHub에 올리고 → 배포 플랫폼에서 "이 저장소와 연결"을 누르면 → 그때부터 코드가 바뀔 때마다 알아서 다시 배포하고 주소를 만들어 줍니다. **"저장 → 올리기 → 자동 배포"** 가 한 줄로 이어지죠. 그리고 이 순간, 어젯밤 친구에게 보냈지만 안 열리던 그 링크가 마침내 어디서든 열립니다.

초보가 가장 많이 막히는 세 곳도 미리 배웠습니다. **① 환경변수 빼먹기** — `.env`는 일부러 GitHub에 안 올리므로 배포 플랫폼 설정 화면에 비밀값을 따로 넣어야 합니다("로컬에선 됐는데 배포하니 안 돼"의 1위 원인). **② CORS 막힘**, **③ 무료의 함정**.

### CORS

화면은 Vercel에, 서버는 Render에 있다면 둘은 서로 다른 집입니다. 서버가 "이 화면에서 오는 요청은 허용"이라고 미리 문을 열어 두지 않으면 브라우저가 **"다른 집 요청은 못 받아"** 라며 막습니다. AI에게는 "내 프론트 주소에서 오는 요청을 허용(CORS)해줘"라고 하면 됩니다.

### 무료 호스팅과 그 함정

공짜의 세계가 계속 줄어드는 중이라는 이야기가 흥미로웠습니다. Heroku는 2022년 11월 무료를 완전히 없앴고 Railway(2023)·Fly.io(2024)도 상시 무료를 거뒀으며 Glitch는 2025년 7월 앱 호스팅을 종료했습니다. 무료 계정을 암호화폐 채굴 같은 곳에 악용하는 사람이 늘었기 때문이라고 합니다.

| 서비스 | 뭘 올리기 좋나 | 주의점 |
|---|---|---|
| Cloudflare Pages | 정적 · 프론트 | 대역폭 무제한 — 트래픽 걱정이 가장 적음 |
| GitHub Pages | 정적 전용 | 가장 단순 |
| Vercel (Hobby) | 프론트 · Next.js | 개인·비상업용만 허용 |
| Netlify | 정적 · 프론트 | 상업적 이용 허용 |
| Render | 백엔드 API | 15분 안 쓰면 잠듦(깨는 데 ~1분) |
| Supabase | 백엔드 + DB | 7일 미사용 시 일시정지 |
| Oracle Always Free | 진짜 리눅스 서버(VM) | 카드 필요 · 설정 어려움 |

함정 셋은 **잠듦**(무료 백엔드는 한동안 아무도 안 오면 잠들어 첫 방문자가 1분쯤 기다립니다 — 고장 아님), **기한·일시정지**(중요한 데이터는 백업을 따로), **요금 폭탄**(예산 알림·상한 걸어 두기)입니다. 무료는 "배우고 시연하기"엔 충분하고, "많은 사람에게 안정적으로 24시간 제공"하는 단계가 오면 그때 유료를 검토하면 됩니다.

### 터널링 — 내 컴퓨터를 서버로

"굳이 남의 서버를 빌려? 내 컴퓨터를 켜 두면 되잖아?"에 대한 답도 있었습니다. 원래는 공유기에 **포트 포워딩**을 걸고 바뀌는 집 주소를 따라갈 **DDNS**가 필요했는데, 집 네트워크가 인터넷에 그대로 노출되고 요즘 많은 가정 회선은 주소 하나를 여러 집이 나눠 쓰는 **CGNAT**라 포트 포워딩 자체가 안 되는 경우가 많습니다.

**터널**은 발상을 뒤집습니다. 밖에서 들어오게 여는 대신 **내 컴퓨터가 바깥 서비스로 먼저 연결을 맺어** 그 통로로 손님을 받습니다. 그래서 포트를 열 필요가 없고 CGNAT도 통과합니다. 잠깐 시연은 **ngrok**(한 줄이면 즉시 공개 주소), 상시용은 **Cloudflare Tunnel**(대역폭 무제한·무료), 개인·팀 내부 공유는 **Tailscale Funnel**이 적합합니다.

결론은 명확했습니다 — 집 서버는 재미있는 공부이자 취미이지만, **남에게 안정적으로 24시간 보여줘야 하는 첫 진짜 배포는 무료 클라우드가 거의 항상 더 안전하고 손이 덜 갑니다.** 원리는 집에서 익히고, 세상에 보여줄 땐 클라우드.

### 프론트-백엔드 연결

실무자들이 "바이브가 죽는 순간"이라 부를 만큼 문제가 몰리는 단계라고 합니다. 가장 안정적인 순서는 **목업 화면 → 백엔드 API 붙이기 → 가짜 데이터를 실제 호출로 교체**이고, 통째로 한 프롬프트에 다 시키는 건 초보에게 거의 항상 실패합니다(AI의 집중력·기억 한계). "데이터 모양 → API → 화면"처럼 작게 쪼개 시켜야 실수를 일찍 잡습니다.

가장 큰 원흉은 **계약 불일치** — 프론트가 기대하는 데이터 모양과 백엔드가 주는 모양이 다른 것입니다. AI를 쓰면 오히려 심해지는데, 양쪽에 '얼추 맞는' 걸 따로 만들어 서서히 어긋나기 때문입니다. 근본 해결책은 **API 명세를 문서로 먼저 남기는 것**이었습니다.

> "엔드포인트 목록과 각 요청/응답 예시(JSON)를 명세 문서로 만들어 줘. 앞으로 이 문서를 기준으로 프론트와 백엔드를 짜자."

기능이 바뀌면 코드보다 이 문서를 먼저 고칩니다. 나머지 습관 셋은 **수직 슬라이스**(층을 나누지 말고 "회원가입 한 기능"을 화면-API-저장까지 하나로 완성하고 바로 테스트), **세 상태 준비**(모든 호출을 로딩/성공/에러로 나눠 각각 화면을 마련), **매 단계 커밋**(AI는 확신에 차서 멀쩡한 걸 망가뜨리기도 합니다)입니다.

내보내기 전 마지막으로 AI에게 한 번 시킬 문장도 배웠습니다 — "이 코드 전체를 하드코딩된 비밀값 · 서버 입력 검증 누락 · CORS 설정 · 인증 취약점 관점으로 점검해 줘." 특히 `NEXT_PUBLIC_`·`VITE_` 접두사가 붙은 값은 "브라우저에 공개"라는 뜻이니 비밀값엔 절대 쓰면 안 됩니다.

## 느낀 점

오늘 배운 것들을 늘어놓으면 용어집처럼 보이지만, 실은 전부 **"내가 만든 화면이 왜 세상과 끊겨 있었나"** 라는 한 질문의 답이었습니다. 그래서 오늘의 산출물은 코드가 아니라 지도라는 말이 와닿았습니다.

지금까지 만든 게임들(`ksk_game`, `drive_game`, `bom_game`, `ksk_game1`)은 전부 GitHub Pages에 올린 화면 단독 서비스였습니다. 오늘 배운 판단 기준으로 보면 그건 서버가 필요 없는 게 맞았고, **랭킹 저장이나 로그인을 붙이려는 순간부터 백엔드가 필요해진다**는 게 이제 분명해졌습니다. 어디에 무엇이 필요한지 구분할 수 있게 된 것이 오늘의 가장 큰 수확입니다.

그리고 AI에 대한 관점이 하나 바뀌었습니다. **AI는 아주 빠른 신입 개발자**라는 비유 — 속도는 놀랍지만 보안·비밀 관리·권한 확인은 감독이 필요하고, 신입에게 "결제 로직을 알아서 안전하게 짜 둬"라고 방치하지는 않는다는 말이 정확했습니다. AI 생성 코드의 45%에 보안 결함이 있다는 숫자는, 지금까지 "돌아가면 됐다"고 생각했던 습관을 돌아보게 만들었습니다. 입력 검증 · 비밀은 환경변수 · 권한 확인(+비밀번호 해시) — 이 셋을 프롬프트로 요구하고 결과를 한 번 더 되묻는 것이, 비전공자가 할 수 있는 가장 강력한 품질 관리라는 결론에 동의합니다.
